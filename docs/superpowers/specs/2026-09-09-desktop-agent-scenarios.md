## 한 장 요약

에이전트가 할 수 있는 일 = **(본다 × 만진다 × 기억한다)의 조합**.
사용자에겐 비서(A), 개발자에겐 동료(B), 데스크탑에겐 면역계(G),
에이전트 사회에겐 주민(F), 그리고 jkdesktop만의 정체성 — **스스로를
고치고 말을 거는 데스크탑**(C 자기 개선 + D 마진 코멘트).

시스템의 심장 한 바퀴:
**관찰 → 코멘트(가설) → 승인 → 수정 → 검증 → 학습 → 더 나은 관찰.**
기록 계층(receipt + 이벤트 버스)이 이 순환의 조상 — 모든 시나리오의
의존성이 여기로 수렴한다 (Part 2.3).

그리고 Round 5에서 밝혀진 확장: 감각은 **창 이벤트에서 끝나지 않는다** —
카메라·마이크·센서·네트워크도 같은 버스에 흐르는 이벤트 소스이고, 같은
권한 모델의 대상이다 (Part 7-N). 데스크탑이 창을 넘어 세계를 보기 시작하는
지점.

**능력 태그**: `[보다]`=구조화 상태/이벤트 읽기, `[만지다]`=창/앱 조작,
`[실행]`=앱 실행·터미널, `[캡처]`=창 픽셀 캡처, `[기억]`=이벤트/receipt 히스토리,
`[협업]`=에이전트 간 통신, `[모델]`=LLM 추론 필요,
Part 7 신설 태그: `[듣다]`=오디오 입력(마이크), `[말하다]`=TTS 출력,
`[카메라]`=카메라 영상, `[연결]`=네트워크/외부 서비스, `[감지]`=센서·장치 상태

## C. 자기 개선 데스크탑 — "매 세션이 끝나면 조금 나아진다"

핵심: 개발 대상과 사용 환경이 같은 머신. 에이전트가 사용자의 불편을
추측이 아닌 관찰로 알고, 수정→빌드→검증→적용 루프를 닫는다.

- **C1 사용 불편 자동 발견** `[기억][모델]`
  "이 버튼 하루 40회 클릭", "이 기능 켰다 끈 적 12번" → 이슈화 → 제안.
- **C2 불평 → 패치 → 카나리 → 적용** `[실행][모델]`
  "태스크바 시계 잘 안 보여" → 브랜치 패치 → 별도 인스턴스 스모크 →
  레이아웃 복원과 함께 재시작 적용 ("재시작하면 반영됩니다" UX).
- **C3 자가수리** `[실행]`
  기본값·키바인딩·사소한 버그는 자동 적용, 큰 변경만 승인 대상.
- **C4 야간 진화** `[실행][모델]`
  밤에 백로그에서 작은 기능 구현 → 아침에 "오늘의 변화 3건" diff 리뷰.
- **C5 취향 학습** `[기억][모델]`
  사용자가 되돌린 변경의 이유를 학습해 다음 제안의 질 향상.
- **C6 역방향: 사용이 곧 개발** `[기억]`
  데스크탑을 쓸수록 에이전트가 커밋/이슈를 생산하는 OS.
- **C7 회귀 감시 기간** `[기억][보다]`
  패치 적용 후 N일간 관련 이벤트 추적 → 이상 징후 시 자동 보고,
  사용자가 되돌리면 그 이유까지 기록.
- **C8 A/B 실험 프레임워크** `[기억][모델]`
  후보 변경 두 가지를 교대로 적용, 사용자의 실제 행동(재사용률, 되돌림 여부)으로
  선호 판정. "감으로"가 아니라 데이터로 취향을 확인.
- **C9 취향 파일** `[기억]`
  사용자의 선호(정렬 순서, 기본 크기, 닫기 습관, 어투)가 구조화된 파일로
  축적 — 모든 에이전트 제안이 이 파일을 참조. 취향은 진화하는 문서.
- **C10 신뢰 통계** `[기억]`
  에이전트 제안의 수용/기각률 공개 → 자율성 단계를 올리고 내리는 근거.
  "이번 달 자가수리 14건, 되돌림 1건".
- **C11 되돌림 일지** `[기억]`
  모든 자동 변경의 기록 + 이유 + 원클릭 롤백. 자기 개선의 안전망.

자율성 사다리: 0 관찰자(리포트만) → 1 제안자(diff 승인) → 2 자가수리(사소한 것
자동) → 3 야간 진화(자율). 신뢰에 따라 시기별로 오르내린다.

방어선: 카나리 배포(별도 인스턴스), git 되돌리기, 승인 게이트, receipt 기록.

## D. 마진 코멘트 — "에이전트가 말을 건다"

문서 코멘트처럼 대상(앵커)에 붙여 개발자에게 전달되는 비침습 메시지.
형태: `{앵커, 작성자, 종류, 증거, 상태, 스레드}`.

- **D1 관찰 코멘트** `[기억]`

# Part 2 — 정리: 단계별 여정과 의존성

구현 단계(플랫폼 스펙의 1~4단계)가 진행될수록 어떤 시나리오가 열리는지,
시나리오 간 의존관계를 정리한다.

## 2.1 단계별 하루 — 각 단계에서 데스크탑의 하루는 이렇게 달라진다

### 1단계 (브로커+MCP) — "외부 에이전트의 하루"

이 시점엔 데스크탑 UI 변화가 없다. 에이전트는 밖(Claude Code 터미널)에서 온다.

```
09:00  Claude Code가 MCP로 접속 → list_windows: "작업 배치 확인"
09:10  launch_app(vplayer) + save_layout("작업") 자동화 스크립트 작성
11:00  빌드 실패 → terminal_exec로 재현 → read_log로 원인 특정
14:00  probes 스모크를 MCP tool 조합으로 재작성 (B1의 씨앗)
17:00  close_window 실험 — receipt에 첫 기록이 쌓임
```

**열리는 시나리오**: B1, B2, B3, B12, F1 (모두 "개발자 동료" 얼굴)
**핵심 성과물**: Desktop Agent API의 실전 검증 + receipt 계층의 첫 데이터

### 2단계 (커맨드 바) — "사용자의 하루"

에이전트가 데스크탑 안으로 들어온다. Alt+Space가 생활이 됨.

```
09:00  "아침" → 업무 레이아웃 복원 + 어제 미완 브리핑 (A2, G7)
10:30  "이 에러 뭐야?" → 포커스된 터미널 질의 (A4)
13:00  vplayer 씬 검색, "다음 트랙" 음성 (E1, A12)
16:00  반복 패턴 감지 → "버튼으로 만들어드릴까요?" 첫 승격 (A3)
18:00  "창 정리해줘" → 청소부 + 개별 승인 (A10)
```

**열리는 시나리오**: A1~A20 대부분, E1~E3
**핵심 성과물**: 자연어→API 경로 확립, 사용자 관점 체감

### 3단계 (자기 개선+코멘트) — "한 주의 순환"

데스크탑이 스스로를 관찰하고, 개발자와 대화하기 시작함.

```
월  관찰: 버튼 클릭 패턴에서 불편 후보 3개 발견 → 관찰 코멘트 (C1, D1)
화  가설: "정렬 불편은 순서 문제" 가설 코멘트 (D3) → 개발자 승인
수  패치: 브랜치 수정 → 카나리 인스턴스 스모크 (C2)
목  적용: 레이아웃 복원과 함께 재시작, 회귀 감시 시작 (C7)
금  판정: 사용 행동으로 가설 검증 → 결과 코멘트 + 취향 파일 갱신 (C5, D2)
금  밤    야간 진화: 백로그에서 작은 기능 하나 구현 (C4)
토  아침  "오늘의 변화 3건" diff 리뷰 → 2건 수용, 1건 기각(사유 학습)
```

**열리는 시나리오**: C 전체, D 전체, G3~G7
**핵심 성과물**: 관찰→가설→수정→판정→학습의 완전한 순환

### 4단계 (생태계) — "에이전트 사회의 한 달"

- 에이전트들이 .jkx로 설치되고, 능력 레지스트리로 협업함 (F2, F5)
- 빌드 실패 → 코더 참여 → 리뷰어 검토의 자동 파이프라인 (F4)
- 외부 세계(메일/캘린더)도 이벤트 버스에 합류 (F9)
- 데스크탑 자체가 하나의 플랫폼으로 판매/공유될 수 있는 상태

**열리는 시나리오**: F 전체, I 전체(장기 진화의 재료가 축적되기 시작)

## 2.2 시나리오 × 단계 매트릭스

| E 미디어·재미 | — | E1~E3 | E4~E11 | — |
| F 생태계 | F1 | — | — | F2~F11 |

3단계=C+D계열 순서가 자연스럽다.

## 2.3 의존성 맵 — 무엇이 무엇의 전제인가

```
[기록 계층: receipt + 이벤트 버스] ← 1단계에서 반드시 먼저
   ├──→ D 코멘트 (증거의 원료)
   │       └──→ C 자기 개선 (코멘트가 백로그)
   │               └──→ I 장기 진화 (시간이 쌓은 결과)
   ├──→ A8 통합검색 / A11 세션복원 / G5 타임라인 / G6 하루요약
   └──→ B2 크래시수사 / B7 재현 / B15 세션서기

[이벤트 버스]
   ├──→ A6 트리거 → 자동화 스크립트 (C의 손)
   ├──→ F 협업 (에이전트 간 통신도 같은 버스)
   └──→ [장치·외부 세계도 토픽 소스] 카메라·마이크·센서·네트워크
         (Part 7-N — 권한 모델의 새 행, 열린 질문 9~11)

[픽셀 캡처] ──→ E4 코치 / E7 회고사진관 / D4 디자인코멘트 / A13 스케치

[ConPTY] ──→ terminal_exec ──→ B1 테스트러너 / C2 자가수리의 실행부

[MCP] ──→ 모든 외부 에이전트의 입구 (1단계의 유일한 프론트)
```

핵심 통찰: **기록 계층(receipt+이벤트)이 모든 것의 조상이다.** 1단계에서
코멘트·자기개선·타임라인이 전부 기록 위에 서므로, 스펙의 receipt/이벤트 버스
설계가 가장 장기적인 투자.

## 2.4 우선순위 관찰 (Round 2 기준 갱신)

- **즉시 가치 + 낮은 비용**: B1(테스트 러너), B3(로그 회귀), F1(MCP) —
  probes·로그·터미널이라는 기존 조각의 조립.
- **정체성**: C+D — Windows에서 불가능하고, 기록 계층(G3/G5)이 전제.
- **쇼케이스**: E4(마인스위퍼 코치) — 캡처 능력의 가장 그림 있는 증명.
- **숨은 조상**: G8(저장 관리인) — 파괴적 자동화의 신뢰를 만드는 첫 벽돌.
- **의외의 조기 구현 후보**: B15(세션 서기) — receipt만 있으면 되고,
  매일 쓰게 되는 기능이므로 에이전트 플랫폼의 "일상화 장치"가 됨.

# Part 3 — 다양화 2차: 시그니처 스토리

시나리오들은 혼자서도 가치 있지만, 조합되면 "데스크탑과 함께 사는 하루"가 된다.
이 섹션은 시나리오들을 서사로 묶어, 시스템이 실제로 어떻게 느껴질지를 상상한다.
(대사는 어조 가제 — 톤은 구현 때 결정)

## S1. 빌드가 깨진 아침 (B1+B2+B4+F4)

```

       → 패널 창: "error C2065 — jkserver.c에 선언 전 사용. 3군데서 발생."
       → receipt에 이 조사 시작 기록
09:14  코더가 패치 제안 + "이 패턴은 B14 검문관이 지난주에도 잡았던 것과 같은
       계열입니다" — 과거 레슨이 자동 연결됨
09:15  사용자 [Apply] → 코더가 빌드 재실행 → probes 스모크 자동 수행 (B1)

```

여기서 중요한 것: 사용자는 이 아침에 타이핑을 딱 두 번 했다 — `[Apply]`와
"봐줘". 나머지는 이벤트 버스가 지휘했다.

## S2. 코멘트의 한 주 (D 전체 + C5 + C9)

월  오전   에이전트가 관찰: "taskbar 버튼 우클릭이 하루 22회, 항상 실패음
           무음" → 관찰 코멘트 D1을 taskbar 버튼에 배지로 부착
화  오후   가설 코멘트 D3: "우클릭은 컨텍스트 메뉴를 기대하실 겁니다.

# Part 4 — 다크 사이드: 이 시스템이 실패하는 법

브레인스토밍의 나머지 절반. 각 시나리오에는 완화책을 붙인다.
(실패 시나리오는 희망적 기능의 역방향 스트레스 테스트다)

- **R1 유령 코멘트**
  UI가 재구성된 후 앵커가 가리키던 요소 소멸 → 코멘트가 존재하지 않는
  버튼 위에 떠 있음. / 완화: D12 자동 마감 + 앵커 무결성 검사.
- **R2 자기개선 진동**
  에이전트가 패치 A 적용 → 3일 후 더 나은 B로 교체 → 다음 주에 A가 다시
  낫다고 판단 → 진동. / 완화: 같은 앵커의 반복 변경에 쿨다운 + C8 A/B로
  판정 전 환전 금지 + C11 일지에서 진동 패턴 자동 감지.
- **R3 취향 오염**
  한 번 잘못 학습된 선호(실수로 기각한 제안을 "싫어함"으로 학습)가 취향
  파일에서 모든 제안을 오염. / 완화: 취향 파일은 사용자가 직접 읽고 수정
  가능(I1), 학습 근거를 함께 기록해 원인 추적 가능.
- **R4 코멘트 피로**
  배지가 UI 도처에 → 허브를 안 열게 됨 → 코멘트 채널의 죽음. / 완화:
  세션 예산, D13 수용 패턴 학습, 기각 주제 재제기 금지.
- **R5 권한 승급 유도**
  합법적 에이전트가 자기 이벤트로 다른 에이전트의 승인 프롬프트를 조작해
  권한 상승 시도. / 완화: 승인 프롬프트는 이벤트 버스 밖(브로커 내부 채널),
  코멘트 스레드와 권한 심사의 분리.
- **R6 반쯤 똑똑한 데스크탑**
  클라우드 단절 → 자연어 커맨드가 반응 없고, 결정적 커맨드만 동작.
  사용자는 어디까지가 로컬인지 모름. / 완화: 기능별 오프라인 계층 명시
  (스펙 §7), 단절 시 "로컬 모드" 배지.
- **R7 세이프모드의 필요**
  에이전트가 데스크탑을 깨뜨려 부팅 불가 → 자기 개선의 최악의 시나리오.
  / 완화: 서버 본체와 에이전트의 격리(브로커는 사이드카), 에이전트 변경은
  항상 브랜치+레이아웃 스냅샷, 부팅 시 에이전트 변경 미적용 옵션.
- **R8 기억의 과잉**
  타임라인이 사용자 의도보다 많이 기억 → 나중에 불편(감시처럼 느껴짐).
  / 완화: G4 프라이버시 스위치, 기본 보존 7일, 기록 전에 무엇이 남는지
  가시화.
- **R9 과의존**
  6개월 후 사용자가 에이전트 없이 데스크탑을 못 쓰게 됨 — 기능이 아니라
  습관의 종속. / 완화: 모든 에이전트 기능은 수동 경로를 항상 유지
  ("에이전트 없이도 데스크탑은 완전하다"를 설계 원칙으로).
- **R10 협업 충돌**
  코더 에이전트와 자가수리가 같은 파일을 동시에 패치. / 완화: 작업 잠금
  토큰(이벤트 버스 상의 리소스 예약), 코디네이터(F10)의 조정.

# Part 5 — 열린 질문 (다음 브레인스토밍 후보)

정리하다가 발견한, 다음 라운드에서 파야 할 구멍들:

3. **세션 복원(A11)의 범위** — 어디까지가 "세션"인가. 재생 위치는?
   브라우저 로그인 상태는? 프라이버시와 편의의 경계.
4. **여러 에이전트의 신원** — 코멘트·receipt에 작성자는 어떻게 표기되고,

5. **코멘트의 어조** — 에이전트가 개발자에게 말을 거는 문체. 존댓말?

6. **실패의 배움** — R1~R10 중 실제로 먼저 일어날 것은 무엇인가.
   자기 개선이 본격화되기 전에 모의 테스트할 방법.
7. **데스크탑 밖의 에이전트와의 경계** — Claude Code 같은 외부 에이전트와
   내장 에이전트가 같은 데스크탑을 조작할 때의 우선순위·잠금 규칙.
8. **receipt의 장기 보존과 가치** — 7일 보존이면 I(장기 진화) 재료가
   부족할 수도. 어떤 것은 오래 남기고 어떤 것은 빨리 지울지의 정책.
9. **장치 I/O의 플랫폼 자리** (Part 7에서 확장) — 카메라/마이크/센서를
   이벤트 소스이자 권한 대상으로 만들려면, 윈도우 서버가 아닌 어디에서
   장치에 접근하는가? 브로커(jkagentd)가 장치 관문도 겸하는가? SDL2 밖의
   장치(웹캠·센서) 접근 라이브러리 선택.
10. **장치 데이터의 로컬 처리 경계** — N1 재실 감지, N27 웨어러블 같은
    카메라/오디오 데이터는 "이미지/음성이 절대 밖으로 나가지 않는" 로컬
    처리 전제. 어느 수준의 모델이 로컬에서 돌 수 있는지, 못 하면 해당
    시나리오를 봉인할지의 정책.
11. **장치 이벤트의 프라이버시 우선순위** — N-카메라 이벤트는 창 이벤트보다
    훨씬 민감. 이벤트 버스의 토픽별 프라이버시 등급(창 이벤트=하, 오디오=중,
    카메라=상)을 권한 모델에 어떻게 녹일지.

# Part 6 — 다양화 3차: 앱별 시나리오와 반공간

## K. 기존 앱별 시나리오 — 데스크탑에 이미 있는 주민들

에이전트는 추상적인 조우가 아니라, 지금 레포에 있는 앱들과 만난다.

- **K1 터미널 × 에이전트** `[보다][실행][모델]`
  실행 중 명령의 실시간 설명, 실패 명령의 재시도 제안, 긴 로그의 하이라이트.
  세션 종료 시 "이 세션에서 한 일" 요약 (B15의 앱 버전).
- **K2 vplayer × 에이전트** `[캡처][기억][모델]`
  jog dial로 계속 뒤로 감는 패턴 감지 → "이 구간 찾으세요? 자막으로
  검색해볼래요?" (E1로 연결). A/V 오프셋 조정 습관 학습 → 미세 보정 제안.
- **K3 브라우저(OSR) × 에이전트** `[보다][모델]`

  개인 버전). 북마크 없이 열어둔 탭의 세션 복원 (A11).
- **K4 taskmgr × 에이전트** `[보다]`
  CPU 스파이크 순간을 taskmgr 데이터로 상관 분석 — "이 순간 OSR 창이
  열렸네요" (B8의 실시간 버전).
- **K5 게임 앱 × 에이전트** `[캡처]`
  마인스위퍼 코치(E4)와 테트리스 하이라이트(E9) — 게임은 캡처 능력의
  최고의 실험장.
- **K6 taskbar × 에이전트** `[기억][보다]`
  taskbar는 셸 특권 클라이언트라 에이전트와의 접점이 특별 — 클릭 패턴이
  UI 개선의 최고 관찰 대상(D8 코드 앵커의 주 고객). 커맨드 바도 여기서
  태어남.
- **K7 스크립트 앱 × 에이전트** `[모델]`
  QuickJS 앱이 `agent.*` 브리지를 쓰는 최초의 예 — scriptdemo가
  "AI 요약 앱"으로 진화하는 과정 자체가 생태계(F3)의 검증.
- **K8 passworddemo × 에이전트** `[보다]`
  오히려 **반대 시나리오**: 비밀번호 입력 창은 observe 금지 대상 —
  에이전트가 봐서는 안 되는 창의 대표 사례 (G4의 상징적 앱).

## L. 반공간 — 에이전트가 "하지 않는" 것의 시나리오

브레인스토밍은 보통 기능을 쌓지만, 이 시스템의 품질은 절제에서 나온다.

- **L1 흐름 속의 침묵** `[기억]`
  사용자가 몰입 상태(긴 무인터럽트 활동, 반복 동작 리듬) → 에이전트는
  아무것도 말하지 않고 관찰만. 제안은 몰입이 끝난 뒤.
- **L2 기각의 존중**
  한 번 기각된 주제는 같은 이유로 다시 제안하지 않음 — 에이전트의 기억은
  회원관리가 아니라 신뢰의 기록.
- **L3 대답하지 않는 질문**
  개인 데이터 경계 밖의 질문(비밀번호, 민감 창 내용) → "그건 못 봐요"가
  기능이 아니라 원칙. K8이 상시 테스트 케이스.
- **L4 조용한 성공**
  사소한 자가수리가 성공해도 매번 알리지 않음 — 주간 다이제스트(D9)로만
  보고. 알림의 가치는 희소성에서 나옴.
- **L5 모르는 것의 인정**
  확신이 없으면 제안 대신 가설 코멘트(D3)로. 에이전트의 확신 표현은
  근거가 있을 때만.
- **L6 사용자의 실수를 목격했을 때**
  잘못된 명령을 조용히 고쳐 실행하는 대신, 항상 한 줄로 확인 — "이거
  ~인데 맞나요?" 실수 바로잡기도 승인을 거침.
- **L7 절제의 수준도 학습된다** `[기억][모델]`
  L1~L6의 임계값(언제 침묵할지, 얼마나 알릴지)도 취향 파일(C9)의
  항목 — 과잉 친절도 소음.

# Part 7 — 다양화 4차: 장치·외부 세계와 미래 앱

Round 4까지의 카탈로그는 윈도우 서버 코어에서 퍼져 나온 탓에 두 가장자리가
비었다: **하드웨어 장치**(카메라·마이크·센서·네트워크)와 **아직 존재하지 않는
앱 카테고리**. 이 파트가 그 두 면을 채운다.

핵심 재해석: 장치는 에이전트의 또 다른 감각기관이자 손발이며, **이벤트 소스이자
권한 대상**이다. 창 이벤트와 카메라 이벤트는 같은 버스에, 같은 권한 모델로
흐른다. 이것이 Windows의 장치 권한 대화상자와 다른 점 — 에이전트·앱·장치가
하나의 권한 체계 안에 있다.

# Part 8 — 다양화 5차: 앱 정복 (App Conquest) — "단순한 앱부터"

사용자 제안(2026-09-09): 단계적 접근에서 **단순한 앱부터 정복해 나가는** 형태.
정복(conquest) = 에이전트가 그 앱을 실행·관찰·조작·검증·회복까지 완주하는 것.
앱 하나가 정복될 때마다 "jkdesktop에서만 되는 자동화"가 하나 생기고 채택률이
올라간다(설계 문서 §6.5와 연동). 기존 probes 스모크(`engine/tools/probes/*.ps1`)
가 각 앱 정복 테스트의 씨앗이다 — 스모크가 정복으로 승격된다.

## P. 앱 정복 시나리오

### 정복의 정의 — 네 가지 문턱

- P1. **관찰**: launch/close/focus + 앱별 이벤트를 구조적으로 받는다 (스크린샷
  추측 금지 — 창 이벤트·로그가 1차 증거, 캡처는 마지막 수단).
- P2. **조작**: 앱의 핵심 루프를 에이전트가 구동한다(스크립트 입력/API 주입).
- P3. **검증**: 상태 단언을 구조적 이벤트/로그로 — 앱의 probe가 회귀 테스트로 승격.
- P4. **회복**: 크래시 → 재실행 + 레이아웃/컨텍스트 복원까지 자동.

### 정복 사다리 (단순 → 복잡, 상태 노면 기준)

- P5. **L0 마인스위퍼** — 단일 창·이산 클릭·로그 판정. probes가 이미 절반을
  검증했다 — 첫 정복 대상. 정복 보상: 보드 관찰 코치(쇼케이스).
- P6. **L1 테트리스** — 60fps 입력 타이밍. 조작 정밀도의 기준점이 된다.
- P7. **L2 passworddemo/scriptdemo** — 이미 스크립트 브리지 위에 있다. 정복 =
  QuickJS에 `agent` tool 노출(스크립트 앱이 에이전트를 부르는 방향).
- P8. **L3 taskmgr** — 읽기 전용 구조화 테이블. 구조적 리드의 원형(pid/CPU가
  픽셀이 아니라 데이터로 온다).
- P9. **L4 터미널** — ConPTY 스트림. 1단계 terminal_exec와 즉시 접합 — 가장
  빨리 정복되는 앱이 될 수 있다(사다리와 병행).
- P10. **L5 일반 ImGui 앱** — 정복 킷 일반화: 새 ImGui 앱 = 스모크 probe +
  트리거 선언 + 회복 레시피 3종 세트.
- P11. **L6 vplayer** — 타이밍 민감 미디어. 조그 자동화·씬 인덱스 검색 검증.
- P12. **L7 브라우저** — CEF OSR 웹 컨텐츠. 가장 어려운 표면 — 마지막 정복.
- P13. **최종 보스: 태스크바/셸 자신** — 특권 클라이언트의 조작(게이트 뒤).
  정복되면 에이전트가 셸 작업까지 돕는다 — 플랫폼 전체가 에이전트 권역.

### 채택 연동

- P14. **정복 배지** — 런처/에이전트 관리자에 "정복됨: minesweeper ✓". 채택의
  게이미피케이션: 정복 앱의 자동화를 실제로 쓴 순간이 채택 이벤트로 기록.
- P15. **정복 순서는 leave_reason가 조정한다** — 사용자가 써보다 나간 앱이
  다음 정복 대상이 된다(§6.5 정체 대응과 동일한 피드백 고리).
- P16. 정복된 앱은 "Windows 데스크탑에서는 불가능한 자동화"의 증거 — 채택
  곡선(S7)의 각 사건이 어느 정복 덕분인지 추적 가능.

## S11. 첫 정복의 밤 — 마인스위퍼 (P5 전체)
