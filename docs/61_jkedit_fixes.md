# docs/61 — JKEdit 결함 픽스 (2026-09-20)

사용자 보고 "JKEdit이 전반적으로 버그 투성이"(docs/46 §7 결함 대장)의 수술.
근본 원인은 두 갈래였다: **KSSM 글리프 폭 무시**(한글 사용자에게 전면 오작동)와
**버퍼(KSSM)↔외부(UTF-8) 경계 무변환**. 개별 증상은 이 둘의 파생이었다.

## 1. 결함 목록과 픽스

| # | 결함 | 원인 | 픽스 |
|---|------|------|------|
| 1 | 멀티라인 선택 미렌더 (대장 기존 결함) | multiline 페인트 분기에 선택 렌더 부재 | 라인×선택 교집합을 3분할 색상(일반/선택 배경+선택 텍스트/일반)으로 렌더 |
| 2 | 한글에서 캐럿·선택·클릭이 밀림 | 좌표 = `바이트×charWidth_(8px)` — JKDC 비트맵 폰트는 ASCII 8px / KSSM 2바이트 16px 전진 | 표시 셀 매핑 신설: `DisplayCells`(범위→8px 셀 수, KSSM 쌍=2셀) + `PosFromCells`(역매핑, 쌍은 통째 전진→반환값이 항상 글리프 경계) |
| 3 | 한글 복사→클립보드 오염 | 버퍼(KSSM) 원바이트를 클립보드에 | 복사 = `KssmToUtf8` 경유 |
| 4 | 한글 붙여넣기 오염 | 클립보드(UTF-8) 원바이트를 KSSM 버퍼에 | 붙여넣기 = `Utf8ToKssm` 경유 |
| 5 | 한글 타이핑이 선택을 살려둠 | `InsertKssmText`/`ProcessHangulKey`에 `DeleteSelection` 누락(ASCII `InsertText`만 있었음) | 양 경로 + `InsertKssmText` 진입점에 `DeleteSelection()` |
| 6 | 한 줄 편집 가로 스크롤 부재 — 길이 초과 시 캐럿 소실 | 수직 스크롤(`firstVisibleLine_`)만 존재 | `firstVisibleCol_`(표시 셀 단위) 신설, `ScrollToCursor`가 캐럿 셀을 밴드로 유지, 페인트·`PixelToPos` 양쪽에 오프셋 반영 |
| 7 | 사소: `DeleteForward`/`SetSelection` 미 스크롤 | — | `ScrollToCursor()` 추가 |

**설계 결정 — 셀 단위 좌표**: KSSM 1글자 = 16px = 2셀(8px 단위)로 보고
캐럿 x = `inner.x + 셀수×8`. 클릭 역매핑은 KSSM 쌍을 통째로 건너뛰므로
쌍 중간 클릭이 자연히 글자 경계에 스냅된다(왼쪽 반 클릭도 글자 뒤에 놓임 —
단순화된 동작, 문서화). `PixelToPos`는 히트 테스트 API로서 private→public 이동.

**`SetText("")` 후 붙여넣기 함정**: 붙여넣기는 커서 위치의 *삽입*이다 — 기존
내용이 남은 버퍼에 ctrl+v하면 2배 길이가 정답이다. 첫 단위 프로브가 이 기대치를
틀려 FAIL을 냈다(코드 결함 아님 — 테스트 정정).

## 2. 검증 (2연속 원칙)

- **`tools/probes/jkedit_probe.cpp` 신설** — JKEdit를 이벤트 시뮬레이션으로
  직접 구동(SDL_SetModState 모디파이어 주입, JKEvent Char/KeyDown). 9체크 ×2
  ALL PASS: KSSM 쌍 원자 클릭 스냅 3건 / 수평 스크롤 / 클립보드 UTF-8 복사 /
  KSSM 붙여넣기 왕복 / 한글 타이핑 선택 대체(오토마타 경로) / Char 경로 선택
  대체(InsertKssmText) / Ctrl+A.
- **probe_workshop ×2 ALL PASS**(createEdit 위젯 경유 회귀, jkclient 경로).
- 전체 ninja 재빌드(ld exit-67 플레이크 + jkagentd 링크 락 + cc1plus OOM —
  `-j3`로 회피, 전부 기존 레슨).

**눈확인 대기(사용자)**: 터미널/워크숍 createEdit에서 ①한글 캐럿 위치 ②멀티라인
선택 강조 ③한글 복붙 ④긴 한 줄 스크롤.

## 3. 레슨

1. **버그 대장의 "전반적 버그 투성이"는 원인 2개로 수렴했다** — 좌표계(셀 매핑)
   과 문자셋 경계(변환). 증상 목록을 원인으로 압축하면 픽스도 테스트도 좁아진다.
2. **프로브 기대치 자체를 검증하라** — 삽입 vs 치환, 전체 선택 범위 같은
   의미론 오해가 FAIL의 반이었다. FAIL 재현 불명 시 먼저 기대치를 의심.
3. JKEvent.text는 char[64] 배열 — 대입 불가, snprintf로.
## 4. 후속 라운드 — 사용자 라이브 보고 (2026-09-20 §2)

사용자 실사용 보고: "testwin 멀티라인에서 한글 입력이 안 보임 + 선택이 안 되는
것 같다". 라이브 진단 결과 두 갈래였다.

### 4.1 앱 보강 — 멀티라인 휠 스크롤 + 긴 줄 클리핑

- **휠 스크롤**: `JKEventType::MouseWheel`은 좌표가 없어 히트테스트 불가 →
  `JKWindow::RespondMessage`가 키 입력처럼 `focusChild_`로 전달(기존 낙하),
  `JKEdit`이 멀티라인에서 `firstVisibleLine_` 가감. dy>0=위.
- **긴 줄 클리핑**: 멀티라인은 가로 스크롤이 없어 상자 폭 초과분이 경계 밖으로
  그려졌다 → 페인트에서 `PosFromCells`(maxCells=inner.w/8)로 `clipEnd` 산출,
  일반/선택 렌더 모두 클립.

### 4.2 시각 프로브의 하네스 갭 — "박스 글리프"의 정체

`jkedit_render_probe.cpp`(신규)가 5케이스 BMP를 뽑았는데 한글이 전부 빈 사각형.
한글이 아니라 **프로브에 `HangulManager`(비트맵 폰트)를 주입하지 않아서**였다 —
`HanPutCh`는 `GetWORDImage` 실패 시 빈 사각형 폴백을 그리고, ASCII는 내장
FONT_8X8 폴백이 있어 멀쩡해 보인다. 폰트 주입 후 한글 글리프+선택 밴드 전부
정상 렌더 확인(단일줄 "한글테스트" '글' 선택, 멀티라인 "한글입력"+Line 1 드래그).
**앱 결함 아님.** 사용자 증상은 17:34 픽스 빌드 이전 스테일 프로세스가 유력 —
재기동 후 재테스트 대기.

- 실행 요령: 프로브는 `engine/build`에서 실행(exe-dir의 `assets/fonts`+SDL DLL
  필요). 프로브 소스 = `tools/probes/jkedit_render_probe.cpp`(정본).
- 멀티라인 END는 **현재 줄 끝**으로 이동(표준) — 버퍼 끝은 Ctrl+End. 시나리오
  프로브에서 한글이 2행에 삽입된 것은 정상 동작.

## 5. 레슨 추가

4. **비트맵 폰트 폴백(빈 사각형)은 "한글 미렌더"로 오독된다** — JKDC는 ASCII
   폴백(내장 8x8)은 있고 한글 폴백은 사각형이다. 시각 프로브는 `HangulManager`
   주입 없이는 한글 케이스를 판정할 수 없다. 폰트 매니저는 프로브 하네스
   기본 장착품으로.
5. **`HanPutCh` 폴백이 렌더 프로브를 통과시켰다** — 기하(셀 위치)는 맞고 글리프만
   미스라 첫 눈확인에서 "정상"으로 오판. 이미지 판독 시 글리프 유무를
   명시적으로 봐야 한다(박스 5개 vs 한글 5글자).
6. **mingw g++ 침묵 사망 = PATH에 `ucrt64/bin` 부재** — cc1plus의 DLL
   (libmpfr/libgmp) 로드 실패가 드라이버 stderr까지 소실되어 exit 1 무출력.
   `PATH="/c/msys64/ucrt64/bin:$PATH"` 선행으로 회복. cwd의 스테일
   `libgmp-10.dll`(engine/build에서 무복사한 것)도 로드를 가로막는다 — 프로브
   디렉에 DLL 통복사 금지, SDL 2종만.
7. **BMP는 하단-업 저장 + Read 도구 PNG 캐시** — 크롭 스크립트는 행 뒤집기
   필수. PNG 컬러 타입 6(RGBA)에 3바이트 RGB 데이터를 넣으면 뷰어가 백색으로
   파싱한다(컬러 타입 2 사용).

## 7. 세 번째 라이브 보고 — "한글 입력하면 안 보임" 라이브 진단 (§8 루트로 수렴)

사용자 재보고: "한글 입력하면 안 보이는 문제 재현 됨", "테스트앱....안보여요".
커밋 약속대로 `state\logs\jkedit_diag.log`에 원문 이벤트 바이트·변환 결과·버퍼
상태를 기록하는 DiagDump를 JKEdit에 심어 라이브 재현을 수집했다.

### 7.1 진단 장비 — DiagDump

- TEXTEDITING/KEYDOWN/CHAR 이벤트마다 `keyCode 16진수 + 버퍼 바이트 덤프`를
  append. 라이브 로그 86줄 확보 후 진단 끝나고 전면 제거(printf류 진단은
  커밋 전 소각 — 레슨 9).
- 라이브 screenshot(shot.ps1)과 로그 디코드를 대조: 버퍼에 "Line 1\nLine 2\n
  Line \n{00,82}{87,61} " 상태에서 화면은 "Line 3행 잘림 + 한글 행 공백".
  **버퍼에는 있는데 렌더가 안 되는 것이 아니라, 버퍼의 첫 NUL이 c_str() 렌더를
  절단**하는 것이었다.

### 7.2 로그가 확정한 것

1. OS IME 경로(TEXTEDITING) 이벤트는 **0건** — SDL 조합 이벤트가 이 환경에서
   도달하지 않는다. 사용자가 F2(내부 자동사 모드)로 전환한 지점(로그 32행)부터
   증상 시작 — **내부 자동사 경로만의 결함**.
2. 34행부터 버퍼에 `{0x00,XX}` NUL 쌍 기록 — 예: `<NUL><8D>`(ㅇ), `<NUL><87>`.
3. 78-79행: 한(D0 65) 완성 직후 `<NUL><82>`(ㄱ)가 한을 **덮어쓴다** — 완성
   음절 소실까지 함께 발생.

## 8. 루트 원인 — 자동사 End1/End2 플러시가 8비트 슬롯 코드를 그대로 배출

`HangulAutomata::Automata`의 End1/End2 종료 상태가 `key`(ConvertKey 출력의
**8비트 자모 슬롯 코드**, 예 ㄱ=0x82)를 outStack에 그대로 넣었다. JKEdit의
`InsertKssmChar`는 16비트를 상하 바이트 KSSM 쌍으로 기록하므로 슬롯 코드는
`{0x00, 0x82}`가 되고 — **std::string 버퍼에 NUL 바이트**가 들어간다. 이후
`dc.TextOut(std::string(view).c_str())` 렌더가 첫 NUL에서 절단 → 한글 행이
통째로 안 보였다. 게다가 End1/End2는 `charCode`(지금까지 조합된 완성 음절)를
버리고 key만 내보냈다 — "한" 타이핑 후 ㄱ이 한을 지우는 증상.

**픽스**:
- `HangulAutomata::ToStandaloneKssm(key8)` 신설 — 슬롯 코드 → 독립 KSSM 2바이트
  코드(자음 `0x8041|(slot<<10)`, 모음 `0x8401|(slot<<5)`, 겹받침 `0x8440|jong`).
  검증: ㄱ(0x82)→0x8841, ㅏ(0xA3)→0x8461, ㄳ(0xC4)→0x8444 — WANCODE.CPP
  SingleHan 표와 일치.
- End1/End2 플러시 = `[charCode(완성 음절), ToStandaloneKssm(key)]` 2글자 배출.
- 방어선: `InsertKssmChar` 선두에서 `code < 0x8000`이면 1회 변환(8비트 슬롯
  코드 유입 전면 차단 — 이 클래스의 결함은 "전면 침묵"이라 다층 방어가 맞다).
- 프로브 T7(End1 시나리오: "한"+ㄱ → 버퍼 D0 65 88 41 = "한ㄱ", NUL 부재,
  KssmToUtf8 왕복) + T8(ToStandaloneKssm 상수 3건) 신설, ×2 ALL PASS.

### 8.1 미수정(기존 동작, 문서화만)

- 단독 모음 후 자음: ㅓ+ㄴ → 채움 초성 음절(0x84E5)로 조합. 원본 AUTOMATA
  semantics 유지.
- Shift+글자가 오타 자모: ConvertKey가 case를 XOR해 대문자 표 행이 죽은 코드 —
  ProcessHangulKey가 modifier=0으로 호출. 별도 과제.
- 조합 중 공백: 자동사 상태가 취소되지 않고 공백 문자만 삽입.

## 9. 레슨 추가

9. **진단 printf는 커밋 전 전량 소각** — DiagDump는 진단 후 즉시 제거했다.
   남겨두면 성능·로그 오염·포맷 문자열 크래시 표면이 남는다.
10. **NUL-in-buffer는 "전면 침묵" 결함 클래스** — std::string+c_str() 렌더
    조합에서 NUL 1바이트는 이후 전부를 지운다. 증상(행 소실)이 원인 위치(
    버퍼 삽입점)에서 멀리 떨어져 보인다. 바이트 덤프 로그가 3분 만에 확정했다.
11. **8비트 슬롯 코드 vs KSSM 2바이트 코드 두 축을 혼용 금지** — 내부 자동사
    표현(슬롯)과 버퍼 표현(KSSM 쌍)의 경계에서 변환 계층(ToStandaloneKssm)을
    강제한다. 방어선을 수신단(InsertKssmChar)에도 둔다.
12. **문자셋 경계는 버퍼↔외부(§1)만이 아니다 — 엔진 내부 표현 간에도 있다.**
    docs/61 §1의 "KSSM↔UTF-8 경계" 교훈의 확장.

## 10. 네 번째 보고 — "오토마타로 조합하는건 이상" = 조합 연쇄 단절 (§8 픽스의 2차 결함)

§8 픽스(완성 글자+새 자모 독립 배출)로 NUL은 막았지만, 새 자모를 **다음 조합의
씨앗**으로 심지 않았다. 받침 뒤 조합이 매번 끊긴다: "한국어" → 한+ㄱ+ㅜ+쓰레기+
어, "것이" → 것+ㅇ+ㅣ. 자모 연쇄의 진실은 "새 자모는 다음 글자의 시작"이다.

### 10.1 픽스 3건

1. **End1/End2 씨앗 심기**: 종료 상태가 (a) 지금까지 조합된 글자를 outStack에
   플러시하고, (b) 트리거 키로 새 조합을 시드(inpStack 재적재, inpSP=1 — 연쇄
   End1 경계 초과 방지)하고 돌아온다. End1 트리거=자음→새 초성, 모음이면 단독
   모음 시드.
2. **End2 받침 넘기기**: 종성+모음(학+ㅗ → 하+고)은 받침을 다음 글자 초성으로
   넘긴다. 플러시는 종성을 뗀 음절(겹받침 DJongsung이면 첫 받침만: inpStack[
   inpSP-2].key 역조회), 씨앗=받침 자음, 트리거 모음은 즉시 중성 조합. 옛
   `inpSP--`는 원본 잔해라 제거.
3. **단독 모음 + 받침 가능 자음 → End1**: 상위 바이트 < 0x88(초성 없음)이면
   받침 대신 모음 플러시+새 초성(옛 동작: 채움 초성 음절 조합 — "강아지"의 ㅈ
   받침 침범). modern IME 동작.

JKEdit 측: complete 후 `curHanState`가 살아 있으면 `InitAutomata()`를 건너뛰고
`outSP`만 비운다(InitAutomata는 시드를 지워 연쇄를 끊는다). 그리고 **조합 중
비(非)조합 입력을 만나면 자동사를 마친다** — 공백/구두점(Char), 이동·삭제·
리턴 키, 마우스 클릭. 마치지 않으면 씨앗 위치가 어긋난 채 다음 키가 엉뚱한
바이트를 덮어쓴다.

### 10.2 부수 픽스 — Shift 자모

ProcessHangulKey가 modifier=0으로 ConvertKey를 불러 Shift+글자가 소문자 자모로
나왔다(대문자 표 행이 죽은 코드). 이제 `shift XOR caps`로 0x0040을 전달 —
ㅆ(Shift+t), ㅃ, ㅉ, ㄲ, ㄸ, ㅒ 입력 가능.

## 12. 다섯 번째 보고 — "랄가 → 랅 → 라가" = End2가 이전 상태를 잃음 (§10.1-2의 오판정)

**픽스**: 키 직전의 상태를 `prevState`로 저장(첫 switch 전)하고 End2의

**레슨 16. 상태 머신에서 "지금 상태"를 검사하는 곳이 이미 상태를 덮은 뒤라면

## 13. 여섯 번째 보고 — "쌍자음은 처음부터 입력이 안됨" = 대문자 키코드 봉쇄

프로브 T14(Shift+r+ㅏ=까)는 통과했는데 라이브에서 쌍자음(ㄲㄸㅃㅆㅉ)이 아예
안 됐다. **원인은 두 층**:

1. `JKEdit::RespondMessage`의 한글 입력 분기가 `ev.keyCode`가 소문자
   `a~z`일 때만 오토마타로 보냈다. **라이브 SDL은 shift를 키코드에 이미
   반영해 'R'(0x52)로 오는데 대문자는 범위 밖이라 분기 자체를 통과 못 해
   조합이 시작도 안 됐다.** "처음부터 입력이 안된다"는 보고의 정체.
2. `ConvertKey`의 `modifier&0x0040 → key^=0x20` XOR는 "소문자 키코드+shift
   플래그"라는 옛 관례(DOS 하니스) 전용이다. 라이브 'R'+shift 플래그에
   XOR하면 오히려 'r'로 되돌아가 평자모 ㄱ이 된다.

**픽스**: ①분기에 대문자 `A~Z` 범위 추가 ②ConvertKey는 isalpha면 먼저
`tolower`로 소문자 통일 후 shift 플래그로만 대문자화 — 키코드 대소문자와
shift 플래그의 두 표현이 어긋나도 "shift 의도" 하나로 수렴한다. 프로브에
라이브 형태 T15('R'+shift+ㅏ=까)/T16('R' 무shift=ㄱ) 신설 — T1~T16(21체크)
×2 ALL PASS, ninja 전체(앱 DLL 전부) 재링크.

**레슨 17. 하니스 경로(소문자 키코드+shift 플래그)가 통과했다고 라이브가
통과인 아니다 — 라이브 SDL은 shift를 키코드에 반영한다. 상태/모디파이어의
"두 표현"이 어긋나는 지점은 정규화 함수 한 곳으로 흡수해야 한다.** T14는
하니스 표현만 검사했으므로 이 결함을 못 잡았다 — 프로브에 표현별 케이스
(라이브 형태/하니스 형태)를 나란히 넣는다.

## 14. 일곱 번째 보고 — "시프트 안먹혀요" = 클라 모드 SDL 모디파이어 미러 부재

§13 픽스에도 라이브에서 Shift가 여전히 안 먹혔다. **원인은 클라/서버 분할
경로**: 서버가 `payload.option = keysym.mod`로 모디파이어를 전달하고 클라가
`ev.option`에 넣기는 하지만(JKClientSurface.cpp), **JKEdit는
`SDL_GetModState()`를 직접 읽는다** — 클라 모드에서는 키 이벤트가 클라
프로세스의 SDL 펌프를 통과하지 않으므로 그 전역 상태가 영원히 갱신되지 않아
shift가 유실됐다. 싱글 프로세스(TranslateSDLEvent)에서만 우연히 올바랐다.

**픽스**: 클라가 KeyDown/KeyUp/MouseDown/MouseUp/MouseWheel 이벤트를 받을 때
`SDL_SetModState(payload.option)`으로 미러링 — 컨트롤 라이브러리 전체가
클라 모드에서 싱글 프로세스와 동일하게 보게 한다. **TEXTINPUT/TEXTEDITING은
미러링하지 않는다** — 그 payload.option은 모디파이어가 아니고, shift 유지
중 KEYDOWN(0x1) 다음 TEXTINPUT(0)으로 덮어쓰면 상태가 파산한다. 프로브 회귀
×2 ALL PASS(이 결함은 콘솔 프로브로 재현 불가 — 클라 경로 결함).

**레슨 18. 컨트롤이 SDL 전역 상태(SDL_GetModState)를 읽는 한 클라 모드는 그
상태를 책임진다 — 이벤트를 큐잉만 하고 전역을 갱신하지 않으면 싱글 프로세스
전용 우연이 된다.** 모디파이어는 ev.option으로 이미 도달하지만 읽는 쪽이
다른 원을 본다 — 데이터는 도착했는데 소비자가 다른 우물을 마시는 클래스.

해제) 후 OS IME 경로 추종 ④`FinishInternalComposition` 신설(씨앗 상태만
남은 경우 InsertKssmChar 확정) ⑤LANG1 핸들러는 키가 안 삼켜지는 환경용으로
유지. 프로브 T18(핸드오버 3체크) 신설, 24체크 ×2 ALL PASS.

"입력은 되는데 전환만 안 먹는다"면 키 전달이 아니라 상태 동기화를 의심한다.**

## 17. 폴링도 실패 — §16의 ImeChanged가 라이브에서 무효였던 두 결함과 저수준 훅으로의 전환

유저 재보고 "전혀 변화 없음". 두 결함이 겹쳤다:

1. **JKWindow가 ImeChanged(및 TextEditing!)를 포커스 컨트롤로 전달하지 않았다**
   — RespondMessage의 포커스 디스패치 목록에 KeyDown/KeyUp/Char/Timer/MouseWheel만
   있어 TextEditing/ImeChanged는 히트테스트 경로(x=y=0)로 떨어져 유실. 서버가
   브로드캐스트해도 편집창에 도달하지 않았다. 부수: 편집 상자의 OS IME 조합
   프리에디트 표시도 이 누락 때문에 죽어 있었다(터미널은 루트 컨트롤이라 우연히
   살아 있었던 것). → 포커스 디스패치에 TextEditing/ImeChanged/ImeToggle 추가.
2. **폴링 관측점 자체가 이 환경에서 죽어 있었다** — 포커스 확실한 진단 창에서
   SendInput VK_HANGUL 토글 전후 `ImmGetOpenStatus/ImmGetConversionStatus`가
   open=0 conv=0 고정(신식 MS 한글 IME는 구형 IMM 변환 플래그를 갱신하지
   않는다). IMM 기반 폴링은 이 환경에서 영원히 발화하지 않는다.

**픽스**: 관측점을 저수준 키보드 훅(WH_KEYBOARD_LL)으로 전환 — IME 가로채기
이전의 원시 VK_HANGUL을 본다. `JKImeHook_win32.cpp` 신설(watchWindow가 전경일
때만 — 다른 앱에서의 한/영 오탐 방지; 훅은 설치 스레드 메시지 펌프에서
발화하므로 서버 Run 루프의 SDL_PollEvent가 배출) → SDL 사용자 이벤트 → 서버가
`InputEventType::ImeToggle`을 포커스 클라에 푸시 → JKEdit 핸들러: 내부 모드만
`FinishInternalComposition()` 후 OS IME 경로 핸드오버(절대 모드 판정은 불가하므
로 하지 않는다 — 기능적으로 중요한 건 내부 조합의 인도뿐). IMM 폴링은
살아 있는 환경용 보조로 유지(ImeChanged는 절대 모드라 멱등). T19(토글
핸드오버 3체크) 신설, 27체크 ×2 ALL PASS.

**레슨 21. 관측점의 죽음은 두 층으로 확인해야 한다 — ①이벤트가 소비자에게
도달하는가(배관) ②관측점 자체가 변화를 보고하는가(플랫폼). "픽스했는데 변화
없음"이면 이 순서로 이분한다.** 신식 IME는 구형 IMM 변환 플래그를 갱신하지
않는다 — Win32 상태 관측은 시대에 따라 부패한다. 알려진 한계: 한자 키(LANG2)
미처리, F2 진입 시 서버 측 IME 영문 강제 채널 미흡(백로그).

## 18. 한/영 토글 완결 — "한글 상태에서도 영문 코드가 온다" 관측이 밝힌 것

유저 관측 "한글 상태에서도 영문이 와서 잘 조합된거 같았는데요" + 재보고 "여전히
한영 전환키는 가능을 안해요". 두 보고를 겹치면 아키텍처 사실이 확정된다:

**이 데스크톱 창에서 OS IME 조합은 사실상 불능이다.** OS IME가 한글 상태여도
SDL엔 영문 원시 키코드(KeyDown)가 오고 내부 오토마타가 전부 조합했다 — 내용
있는 TEXTEDITING/TEXTINPUT이 이 창에 도달하지 않는다(§17의 빈 버스트만 관측).
그러므로 §16.1의 ImeToggle 핸드오버(내부→ImeHangul 손떼기)는 두 결함이었다:

1. ImeHangul로 손을 떼면 OS IME가 조합해 주지 않으니 **한국어 입력이 사망**한다.
   (영문은 Char(TEXTINPUT) 경로로 살아 있어 영문 전환은 우연히 동작했다.)
2. 핸들러가 `inputMode_ == InternalHangul`일 때만 동작하므로 **ImeHangul/Ascii
   상태에선 no-op** — 한/영으로는 한국어를 다시 켤 방법이 영원히 없었다. F2만
   양방향. 유저 보고 "한영 전환키는 가능을 안해요"의 정체.

**픽스 — 한/영 = F2와 동일한 내부 모드 양방향 토글**:
- `ImeToggle`(저수준 훅)과 `LANG1`(키코드 정통 도달 환경용) 핸들러를 통일:
  `FinishInternalComposition()`(조합 중이면 확정) + `ToggleHangulMode()` +
  `SilenceOsIme()`(신설 헬퍼 — F2의 인라인 OS IME ASCII 강제를 추출).
- **단일 소유 규칙(§18 방어선)**: InternalHangul 모드에선 TEXTEDITING 선조합을
  버리고, 비ASCII Char(OS IME 커밋이 유일 발생원)도 버린다 — OS IME가 살아
  있는 환경에서의 이중 조합을 봉쇄. ImeChanged 폴링은 IMM이 살아 있는 환경용
  보조로 유지(T18 무변경).
- 프로브 T19를 토글 의미로 재작성(T19a 내부→Ascii 확정 / T19c Ascii→내부
  재진입=옛 코드 사망점 / T19c2 재진입 후 조합 "바" / T19d 단일 소유 2체크),
  27체크 ×2 ALL PASS.

**레슨 22. 유저의 우연한 관측("영문이 왔다")은 아키텍처 단서다 — OS IME가
한글인데 영문 코드가 조합된다면 OS IME 조합 경로는 불능이고, 그러면 그 경로로
손을 떼는 설계(핸드오버)는 전부 사망 경로다.** 토글류는 "관측한 환경의 상태를
따라간다"가 아니라 "자기 소유 체계를 뒤집는다"로 구현하는 게 안전 — 절대 상태를
못 읽는 플랫폼에서 상태 따라가기는 상태 봉인이 된다. 알려진 한계: 한자 키(LANG2)
미처리, 클라→서버 IME 강제 채널(백로그, 클라 모드의 SilenceOsIme는 no-op).

## 19. 조합 중 백스페이스 자소 되돌림 + LL 훅 wParam 결함 — 두 보고 동시 수리

**보고 1**: "back 키에서 자소 단위 제거가 아니라 조합중인 글자가 다 날아가네요?"
— 표준 IME는 조합 중 백스페이스를 자소 단위 되돌림(가→ㄱ→빈)으로 처리하는데
`DeleteBackward`가 조합 중 자동사를 통째로 취소하고 쌍 전체를 지우도록 명시돼
있었다.

**픽스**: 자동사가 이미 키마다 "적용 후" 상태 스냅샷을 inpStack에 쌓고 있으므로
**한 칸 pop = 자소 1개 제거**가 정확히 성립한다. `HangulAutomata::BackspaceJamo`
신설(pop 후 inpStack[inpSP-1]로 상태 복원, 되돌린 음절 코드 반환) +
`DeleteBackward`는 조합 쌍을 되돌린 코드로 제자리 재기록, 스택이 시드뿐이면
쌍 제거+초기화. 겹받치 음절도 랄→라→ㄹ→빈으로 풀린다.

**한계**: 받침 넘김(학+ㅗ→하+고) 뒤 백스페이스는 고 씨앗만 pop해 "하"가 남는다
— 넘어간 받침 ㄱ의 재부착(학 복원)은 End2 플러시 이력을 자동사가 갖지 않아
불가(MS IME와 다른 점, 백로그).

**보고 2**: "한영키는 아예 안날아오는거 같아요" — §17 LL 훅이 **한 번도 발화한
적이 없었다**. LL 훅 콜백의 wParam은 메시지 종류(WM_KEYDOWN=0x100)이고 가상키는
`KBDLLHOOKSTRUCT::vkCode`에 있다. 옛 코드가 `wParam == VK_HANGUL`(0x15)로 검사해
WM_KEYDOWN과 절대 일치하지 않았다. → `wParam == WM_KEYDOWN/WM_SYSKEYDOWN &&
info->vkCode == VK_HANGUL`로 수정. 서버 측에 훅 발화+전달 대상 로그 1행 추가
(라이브 진단 증거). 유저의 이전 보고 "여전히 가능을 안해요"의 진짜 정체는
"토글 의미"가 아니라 **이벤트 무도달**이었다 — §18의 토글 통일은 여전히 옳은
수정(도달해도 한 방향이었음)이지만, 발화 자체가 죽어 있었다.

**레슨 23. 하니스가 통과 안 하는 층은 하니스로 검증할 수 없다 — LL 훅은 OS
입력 계층이므로 유닛 프로브가 전혀 거치지 않는다. "픽스했는데 변화 없음"이
두 번 반복되면(§16 폴링→§17 훅) 관측점 파이프라인 전체를 처음부터 단계별로
재검증한다: 콜백 진입 조건(여기서 파산)→SDL 푸시→서버 전달→클라 번역.**
라이브 증거는 서버 로그(`[ime] toggle -> client N`)로 남긴다.

## 20. 뿌리 결함 교차검토 — "이 결함들의 원인이 다른 데도 영향 줬나?"

유저 요청 검토. 뿌리 결함별로 같은 패턴의 잠복 결함을 전수 확인했다:

1. **LL 훅 wParam/vkCode(§19)** — LL 훅은 코드베이스에 JKImeHook 하나뿐. 타
   영향 없음. ✓
2. **SDL 전역 모디파이어 직독(§14)** — 클라 모드에서 전역이 죽는 클래스. 직독자
   20여 곳(RecogApp/IconEditApp/VectorApp/VectorFontApp의 Alt+X, 브라우저,
   터미널, imgui 백엔드 등) 전부 커버 확인 — §14 픽스가 JKClientSurface에서
   키/마우스 이벤트마다 SDL_SetModState 미러링하므로 시스템적 해결.
   imgui 백엔드는 이미 ev.option 직용(문서화돼 있음). ✓
3. **소문자 범위 검사만 있는 키코드 블록(§13 계열)** — JKEdit는 픽스, 터미널
   Ctrl+letter는 애초 대소문자 양쪽 처리(764-785행). **ClientBrowserApp
   SdlKeyToVk만 소문자 전용** — 라이브 shift+letter('R')가 VK 변환 탈락.
   → 대문자 범위 추가 픽스(VK는 대소문자 무관). 서버의 나머지 a-z 검사는
   지문/토픽 문자열 파싱이라 무관. ✓
4. **★OS IME 조합 불능의 진짜 원인 — 우리가 의도적으로 뗐었다**: 서버 Init의
   `JKPlatform::DetachIme(window_)`(9cade2d, 2026-09-06)가
   ImmAssociateContext(hwnd, NULL)로 서버 창의 IME 컨텍스트를 떼어낸다.
   사유(주석): IME가 붙으면 Enter/Esc/letters가 VK_PROCESSKEY로 가로채져
   클라가 원시 키다운을 못 받는다. **§18의 "OS IME가 불능인 미스터리"는 기계
   특성이 아니라 이 설계였다**(§18 문서 정정). 그리고 이 설계의 희생자가
   하나 있다:
   - **터미널은 데스크톱에서 한글 입력이 처음부터 죽어 있다** — 터미널은 OS IME
     커밋(Char/TEXTEDITING, docs/26 단계 5)에 의존하는데 서버 창엔 IME가
     없다. 영어/Ctrl은 원시 키 전달이라 살아 있어 지금까지 미감지.
     jkedit/testwin의 내부 오토마타는 원시 키로 조합하므로 무사 — 터미널만
     OS IME 의존이 유일했다.
   - **수정 방향 = 터미널에 내부 오토마타 이식**: HangulAutomata 재사용 +
     preEdit_ 오버레이(조합 표시) + BackspaceJamo(자소 백스페이스). IME를
     다시 붙이는 방향은 VK_PROCESSKEY 스왈로우가 원시 키 전달을 깨므로 부적.
     "내부 오토마타가 데스크톱의 한국어를 전부 소유"하는 §18 아키텍처의
     완결. 별도 작업(pty 상호작용 엣지: 조합 중 리턴/붙여넣기/포커스 상실).
   - vplayer 경로 필드 등은 ASCII 전용, jkchat/폰 브리지는 독자 창·프로세스라
     자체 IME 소유 — 무관.
5. **NUL-in-buffer(§8)** — 슬롯 코드 소비자는 JKEdit뿐(JKHangulManager는 폰트
   렌더링 전용). ✓
6. **JKWindow 이벤트 디스패치 누락(§17-1)** — TextEditing 소비자는 JKEdit와
   TerminalView뿐, 둘 다 이제 포커스 디스패치로 커버. ✓

**레슨 24. "뿌리 결함 교차검토"는 결함 수리 후 정기 의제다 — 한 뿌리가 여러
증상을 낳는 경우, 유저가 아직 만나지 못한 증상(latent)이 가장 위험하다. 검토
출력은 ①같은 패턴의 직독자 전수 ②그 패턴의 유일 소비자 ③설계상 의도된
동작이 다른 기능의 전제를 깨는가(IME detach vs 터미널)의 세 축으로.**

## 21. 캡스락 상태 한글 조합 쌍자음 — shift XOR caps의 잘못된 일반화

유저 보고 "CAPS LOCK 상태에서 한글 입력시 쌍자음이 입력됨". 겹자모(쌍자음) 행
선택 플래그를 `(shift != caps) ? 0x0040 : 0`으로 넘기고 있었다 — 캡스락이
켜져 있으면 Shift 없이도 플래그가 켜져 평자모 키가 겹자모 행(한글 자판의
대문자 행)으로 들어갔다. XOR는 "WM_CHAR류에서 shift+caps=소문자, caps=대문자"
관례를 자모 의도로 일반화한 실수 — 캡스락의 대소문자는 keycode와
ConvertKey의 tolower 정규화(§13)가 이미 흡수하는 정보라 자모 의도와 무관하다.

**픽스**: 겹자모 플래그는 `(mod & KMOD_SHIFT)`만. 캡스락 단독 → 평자모(두
키코드 표현 모두 — SDL이 캡스를 키코드에 반영하는 경로 'R'과 반영하지 않는
경로 'r' 전부), Shift+캡스 병용은 Shift가 이긴다(겹자모 — 표준 IME 관례).
T21 신설(캡스 소문자/캡스 대문자 키코드/Shift 우승 3체크), 38체크 ×2 ALL PASS.

**레슨 25. 모디파이어 조합 로직은 "키코드가 이미 반영한 정보"와 겹치면 안
된다 — keycode가 대소문자를 이미 담고 있으면(라이브 SDL) 플래그는 오직
키코드에 없는 정보(shift 의도)만 운반해야 한다. XOR로 두 근원을 합치면 한
근원(caps)이 다른 의미를 끌어온다.**
