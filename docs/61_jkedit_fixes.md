# docs/61 — JKEdit 결함 픽스 (2026-09-20)

사용자 보고 "JKEdit이 전반적으로 버그 투성이"(docs/46 §7 결함 대장)의 수술.
근본 원인은 두 갈래였다: **KSSM 글리프 폭 무시**(한글 사용자에게 전면 오작동)와
**버퍼(KSSM)↔외부(UTF-8) 경계 무변환**. 개별 증상은 이 둘의 파생이었다.

## 1. 결함 목록과 픽스

| # | 결함 | 원인 | 픽스 |
|---|------|------|------|
| 1 | 멀티라인 선택 미렌더 (대장 기존 결함) | multiline 페인트 분기에 선택 렌더 부재 | 라인×선택 교집합을 3분할 색상(일반/선택 배경+선택 텍스트/일반)으로 렌더 |
| 2 | 한글에서 캐럿·선택·클릭이 밀림 | 좌표 = `바이트×charWidth_(8px)` — JKDC 비트맵 폰트는 ASCII 8px / KSSM 2바이트 16px 전진 | 표시 셀 매핑 신설: `DisplayCells`(범위→8px 셀 수, KSSM 쌍=2셀) + `PosFromCells`(역매핑, 쌍은 통째 전진→반환값이 항상 글리프 경계) |
| 3 | 한글 복사→클립보드 오염 | 버퍼(KSSM) 원바이트를 클립보드에 | 복사 = `KssmToUtf8` 경유 |
| 4 | 한글 붙여넣기 오염 | 클립보드(UTF-8) 원바이트를 KSSM 버퍼에 | 붙여넣기 = `Utf8ToKssm` 경유 |
| 5 | 한글 타이핑이 선택을 살려둠 | `InsertKssmText`/`ProcessHangulKey`에 `DeleteSelection` 누락(ASCII `InsertText`만 있었음) | 양 경로 + `InsertKssmText` 진입점에 `DeleteSelection()` |
| 6 | 한 줄 편집 가로 스크롤 부재 — 길이 초과 시 캐럿 소실 | 수직 스크롤(`firstVisibleLine_`)만 존재 | `firstVisibleCol_`(표시 셀 단위) 신설, `ScrollToCursor`가 캐럿 셀을 밴드로 유지, 페인트·`PixelToPos` 양쪽에 오프셋 반영 |
| 7 | 사소: `DeleteForward`/`SetSelection` 미 스크롤 | — | `ScrollToCursor()` 추가 |

**설계 결정 — 셀 단위 좌표**: KSSM 1글자 = 16px = 2셀(8px 단위)로 보고
캐럿 x = `inner.x + 셀수×8`. 클릭 역매핑은 KSSM 쌍을 통째로 건너뛰므로
쌍 중간 클릭이 자연히 글자 경계에 스냅된다(왼쪽 반 클릭도 글자 뒤에 놓임 —
단순화된 동작, 문서화). `PixelToPos`는 히트 테스트 API로서 private→public 이동.

**`SetText("")` 후 붙여넣기 함정**: 붙여넣기는 커서 위치의 *삽입*이다 — 기존
내용이 남은 버퍼에 ctrl+v하면 2배 길이가 정답이다. 첫 단위 프로브가 이 기대치를
틀려 FAIL을 냈다(코드 결함 아님 — 테스트 정정).

## 2. 검증 (2연속 원칙)

- **`tools/probes/jkedit_probe.cpp` 신설** — JKEdit를 이벤트 시뮬레이션으로
  직접 구동(SDL_SetModState 모디파이어 주입, JKEvent Char/KeyDown). 9체크 ×2
  ALL PASS: KSSM 쌍 원자 클릭 스냅 3건 / 수평 스크롤 / 클립보드 UTF-8 복사 /
  KSSM 붙여넣기 왕복 / 한글 타이핑 선택 대체(오토마타 경로) / Char 경로 선택
  대체(InsertKssmText) / Ctrl+A.
- **probe_workshop ×2 ALL PASS**(createEdit 위젯 경유 회귀, jkclient 경로).
- 전체 ninja 재빌드(ld exit-67 플레이크 + jkagentd 링크 락 + cc1plus OOM —
  `-j3`로 회피, 전부 기존 레슨).

**눈확인 대기(사용자)**: 터미널/워크숍 createEdit에서 ①한글 캐럿 위치 ②멀티라인
선택 강조 ③한글 복붙 ④긴 한 줄 스크롤.

## 3. 레슨

1. **버그 대장의 "전반적 버그 투성이"는 원인 2개로 수렴했다** — 좌표계(셀 매핑)
   과 문자셋 경계(변환). 증상 목록을 원인으로 압축하면 픽스도 테스트도 좁아진다.
2. **프로브 기대치 자체를 검증하라** — 삽입 vs 치환, 전체 선택 범위 같은
   의미론 오해가 FAIL의 반이었다. FAIL 재현 불명 시 먼저 기대치를 의심.
3. JKEvent.text는 char[64] 배열 — 대입 불가, snprintf로.
## 4. 후속 라운드 — 사용자 라이브 보고 (2026-09-20 §2)

사용자 실사용 보고: "testwin 멀티라인에서 한글 입력이 안 보임 + 선택이 안 되는
것 같다". 라이브 진단 결과 두 갈래였다.

### 4.1 앱 보강 — 멀티라인 휠 스크롤 + 긴 줄 클리핑

- **휠 스크롤**: `JKEventType::MouseWheel`은 좌표가 없어 히트테스트 불가 →
  `JKWindow::RespondMessage`가 키 입력처럼 `focusChild_`로 전달(기존 낙하),
  `JKEdit`이 멀티라인에서 `firstVisibleLine_` 가감. dy>0=위.
- **긴 줄 클리핑**: 멀티라인은 가로 스크롤이 없어 상자 폭 초과분이 경계 밖으로
  그려졌다 → 페인트에서 `PosFromCells`(maxCells=inner.w/8)로 `clipEnd` 산출,
  일반/선택 렌더 모두 클립.

### 4.2 시각 프로브의 하네스 갭 — "박스 글리프"의 정체

`jkedit_render_probe.cpp`(신규)가 5케이스 BMP를 뽑았는데 한글이 전부 빈 사각형.
한글이 아니라 **프로브에 `HangulManager`(비트맵 폰트)를 주입하지 않아서**였다 —
`HanPutCh`는 `GetWORDImage` 실패 시 빈 사각형 폴백을 그리고, ASCII는 내장
FONT_8X8 폴백이 있어 멀쩡해 보인다. 폰트 주입 후 한글 글리프+선택 밴드 전부
정상 렌더 확인(단일줄 "한글테스트" '글' 선택, 멀티라인 "한글입력"+Line 1 드래그).
**앱 결함 아님.** 사용자 증상은 17:34 픽스 빌드 이전 스테일 프로세스가 유력 —
재기동 후 재테스트 대기.

- 실행 요령: 프로브는 `engine/build`에서 실행(exe-dir의 `assets/fonts`+SDL DLL
  필요). 프로브 소스 = `tools/probes/jkedit_render_probe.cpp`(정본).
- 멀티라인 END는 **현재 줄 끝**으로 이동(표준) — 버퍼 끝은 Ctrl+End. 시나리오
  프로브에서 한글이 2행에 삽입된 것은 정상 동작.

## 5. 레슨 추가

4. **비트맵 폰트 폴백(빈 사각형)은 "한글 미렌더"로 오독된다** — JKDC는 ASCII
   폴백(내장 8x8)은 있고 한글 폴백은 사각형이다. 시각 프로브는 `HangulManager`
   주입 없이는 한글 케이스를 판정할 수 없다. 폰트 매니저는 프로브 하네스
   기본 장착품으로.
5. **`HanPutCh` 폴백이 렌더 프로브를 통과시켰다** — 기하(셀 위치)는 맞고 글리프만
   미스라 첫 눈확인에서 "정상"으로 오판. 이미지 판독 시 글리프 유무를
   명시적으로 봐야 한다(박스 5개 vs 한글 5글자).
6. **mingw g++ 침묵 사망 = PATH에 `ucrt64/bin` 부재** — cc1plus의 DLL
   (libmpfr/libgmp) 로드 실패가 드라이버 stderr까지 소실되어 exit 1 무출력.
   `PATH="/c/msys64/ucrt64/bin:$PATH"` 선행으로 회복. cwd의 스테일
   `libgmp-10.dll`(engine/build에서 무복사한 것)도 로드를 가로막는다 — 프로브
   디렉에 DLL 통복사 금지, SDL 2종만.
7. **BMP는 하단-업 저장 + Read 도구 PNG 캐시** — 크롭 스크립트는 행 뒤집기
   필수. PNG 컬러 타입 6(RGBA)에 3바이트 RGB 데이터를 넣으면 뷰어가 백색으로
   파싱한다(컬러 타입 2 사용).

## 7. 세 번째 라이브 보고 — "한글 입력하면 안 보임" 라이브 진단 (§8 루트로 수렴)

사용자 재보고: "한글 입력하면 안 보이는 문제 재현 됨", "테스트앱....안보여요".
커밋 약속대로 `state\logs\jkedit_diag.log`에 원문 이벤트 바이트·변환 결과·버퍼
상태를 기록하는 DiagDump를 JKEdit에 심어 라이브 재현을 수집했다.

### 7.1 진단 장비 — DiagDump

- TEXTEDITING/KEYDOWN/CHAR 이벤트마다 `keyCode 16진수 + 버퍼 바이트 덤프`를
  append. 라이브 로그 86줄 확보 후 진단 끝나고 전면 제거(printf류 진단은
  커밋 전 소각 — 레슨 9).
- 라이브 screenshot(shot.ps1)과 로그 디코드를 대조: 버퍼에 "Line 1\nLine 2\n
  Line \n{00,82}{87,61} " 상태에서 화면은 "Line 3행 잘림 + 한글 행 공백".
  **버퍼에는 있는데 렌더가 안 되는 것이 아니라, 버퍼의 첫 NUL이 c_str() 렌더를
  절단**하는 것이었다.

### 7.2 로그가 확정한 것

1. OS IME 경로(TEXTEDITING) 이벤트는 **0건** — SDL 조합 이벤트가 이 환경에서
   도달하지 않는다. 사용자가 F2(내부 자동사 모드)로 전환한 지점(로그 32행)부터
   증상 시작 — **내부 자동사 경로만의 결함**.
2. 34행부터 버퍼에 `{0x00,XX}` NUL 쌍 기록 — 예: `<NUL><8D>`(ㅇ), `<NUL><87>`.
3. 78-79행: 한(D0 65) 완성 직후 `<NUL><82>`(ㄱ)가 한을 **덮어쓴다** — 완성
   음절 소실까지 함께 발생.

## 8. 루트 원인 — 자동사 End1/End2 플러시가 8비트 슬롯 코드를 그대로 배출

`HangulAutomata::Automata`의 End1/End2 종료 상태가 `key`(ConvertKey 출력의
**8비트 자모 슬롯 코드**, 예 ㄱ=0x82)를 outStack에 그대로 넣었다. JKEdit의
`InsertKssmChar`는 16비트를 상하 바이트 KSSM 쌍으로 기록하므로 슬롯 코드는
`{0x00, 0x82}`가 되고 — **std::string 버퍼에 NUL 바이트**가 들어간다. 이후
`dc.TextOut(std::string(view).c_str())` 렌더가 첫 NUL에서 절단 → 한글 행이
통째로 안 보였다. 게다가 End1/End2는 `charCode`(지금까지 조합된 완성 음절)를
버리고 key만 내보냈다 — "한" 타이핑 후 ㄱ이 한을 지우는 증상.

**픽스**:
- `HangulAutomata::ToStandaloneKssm(key8)` 신설 — 슬롯 코드 → 독립 KSSM 2바이트
  코드(자음 `0x8041|(slot<<10)`, 모음 `0x8401|(slot<<5)`, 겹받침 `0x8440|jong`).
  검증: ㄱ(0x82)→0x8841, ㅏ(0xA3)→0x8461, ㄳ(0xC4)→0x8444 — WANCODE.CPP
  SingleHan 표와 일치.
- End1/End2 플러시 = `[charCode(완성 음절), ToStandaloneKssm(key)]` 2글자 배출.
- 방어선: `InsertKssmChar` 선두에서 `code < 0x8000`이면 1회 변환(8비트 슬롯
  코드 유입 전면 차단 — 이 클래스의 결함은 "전면 침묵"이라 다층 방어가 맞다).
- 프로브 T7(End1 시나리오: "한"+ㄱ → 버퍼 D0 65 88 41 = "한ㄱ", NUL 부재,
  KssmToUtf8 왕복) + T8(ToStandaloneKssm 상수 3건) 신설, ×2 ALL PASS.

### 8.1 미수정(기존 동작, 문서화만)

- 단독 모음 후 자음: ㅓ+ㄴ → 채움 초성 음절(0x84E5)로 조합. 원본 AUTOMATA
  semantics 유지.
- Shift+글자가 오타 자모: ConvertKey가 case를 XOR해 대문자 표 행이 죽은 코드 —
  ProcessHangulKey가 modifier=0으로 호출. 별도 과제.
- 조합 중 공백: 자동사 상태가 취소되지 않고 공백 문자만 삽입.

## 9. 레슨 추가

9. **진단 printf는 커밋 전 전량 소각** — DiagDump는 진단 후 즉시 제거했다.
   남겨두면 성능·로그 오염·포맷 문자열 크래시 표면이 남는다.
10. **NUL-in-buffer는 "전면 침묵" 결함 클래스** — std::string+c_str() 렌더
    조합에서 NUL 1바이트는 이후 전부를 지운다. 증상(행 소실)이 원인 위치(
    버퍼 삽입점)에서 멀리 떨어져 보인다. 바이트 덤프 로그가 3분 만에 확정했다.
11. **8비트 슬롯 코드 vs KSSM 2바이트 코드 두 축을 혼용 금지** — 내부 자동사
    표현(슬롯)과 버퍼 표현(KSSM 쌍)의 경계에서 변환 계층(ToStandaloneKssm)을
    강제한다. 방어선을 수신단(InsertKssmChar)에도 둔다.
12. **문자셋 경계는 버퍼↔외부(§1)만이 아니다 — 엔진 내부 표현 간에도 있다.**
    docs/61 §1의 "KSSM↔UTF-8 경계" 교훈의 확장.

## 10. 네 번째 보고 — "오토마타로 조합하는건 이상" = 조합 연쇄 단절 (§8 픽스의 2차 결함)

§8 픽스(완성 글자+새 자모 독립 배출)로 NUL은 막았지만, 새 자모를 **다음 조합의
씨앗**으로 심지 않았다. 받침 뒤 조합이 매번 끊긴다: "한국어" → 한+ㄱ+ㅜ+쓰레기+
어, "것이" → 것+ㅇ+ㅣ. 자모 연쇄의 진실은 "새 자모는 다음 글자의 시작"이다.

### 10.1 픽스 3건

1. **End1/End2 씨앗 심기**: 종료 상태가 (a) 지금까지 조합된 글자를 outStack에
   플러시하고, (b) 트리거 키로 새 조합을 시드(inpStack 재적재, inpSP=1 — 연쇄
   End1 경계 초과 방지)하고 돌아온다. End1 트리거=자음→새 초성, 모음이면 단독
   모음 시드.
2. **End2 받침 넘기기**: 종성+모음(학+ㅗ → 하+고)은 받침을 다음 글자 초성으로
   넘긴다. 플러시는 종성을 뗀 음절(겹받침 DJongsung이면 첫 받침만: inpStack[
   inpSP-2].key 역조회), 씨앗=받침 자음, 트리거 모음은 즉시 중성 조합. 옛
   `inpSP--`는 원본 잔해라 제거.
3. **단독 모음 + 받침 가능 자음 → End1**: 상위 바이트 < 0x88(초성 없음)이면
   받침 대신 모음 플러시+새 초성(옛 동작: 채움 초성 음절 조합 — "강아지"의 ㅈ
   받침 침범). modern IME 동작.

JKEdit 측: complete 후 `curHanState`가 살아 있으면 `InitAutomata()`를 건너뛰고
`outSP`만 비운다(InitAutomata는 시드를 지워 연쇄를 끊는다). 그리고 **조합 중
비(非)조합 입력을 만나면 자동사를 마친다** — 공백/구두점(Char), 이동·삭제·
리턴 키, 마우스 클릭. 마치지 않으면 씨앗 위치가 어긋난 채 다음 키가 엉뚱한
바이트를 덮어쓴다.

### 10.2 부수 픽스 — Shift 자모

ProcessHangulKey가 modifier=0으로 ConvertKey를 불러 Shift+글자가 소문자 자모로
나왔다(대문자 표 행이 죽은 코드). 이제 `shift XOR caps`로 0x0040을 전달 —
ㅆ(Shift+t), ㅃ, ㅉ, ㄲ, ㄸ, ㅒ 입력 가능.

### 10.3 검증

프로브 T9~T12 신설: "한국어" 완성 / "하고" 종성 넘김(하+고) / "ㅓ나" 단독 모음 /
Shift+t=ㅆ. T1~T12 ×2(+3차) ALL PASS. probe_workshop ×2 ALL PASS. ninja 전체
재빌드(jkdesktop.exe+앱 DLL 21:16) 후 서버·브리지 재기동.

## 11. 레슨 추가

13. **조합형 오토마타의 불변식: "종료 상태의 트리거 키는 다음 조합의 씨앗"** —
    종료 처리가 키를 소비해 숨기면 조합 연쇄가 끊긴다. End2(종성+모음)는 받침을
    초성으로 넘기고 트리거 모음을 즉시 중성으로 조합하는 2단 동작.
14. **상태 머신 픽스는 "연쇄" 케이스를 테스트하라** — 단일 키 시나리오(T7)만으로
   는 씨앗 소실을 못 잡았다. "한국어"(End1 연쇄)/"하고"(End2 넘기기) 같은
    완성 단어 테스트가 2차 결함을 잡았다.
15. **부수 상태(residual flags)와의 상호작용을 문서화** — 조합 상태는 JKEdit의
    composing_과 자동사 내부 상태의 이중 관리다. 한쪽만 리셋하면(InitAutomata만
    호출) 어긋난 씨앗이 다른 바이트를 덮어쓴다. "비조합 입력 발생 시 양쪽을
    함께 마친다"가 계약.

## 12. 다섯 번째 보고 — "랄가 → 랅 → 라가" = End2가 이전 상태를 잃음 (§10.1-2의 오판정)

"랄가"(ㄹㅏㄹㄱㅏ) 입력: 랄+ㄱ이 겹받침 ㄺ으로 조합(랅)된 후 모음이 오면
첫 받침 ㄹ만 남긴 "랄" 플러시+ㄱ 새 초성이어야 하는데 "라가"(받침 탈락)가 됐다.
**원인: End2 분기에서 `curHanState == DJongsung`을 판정했지만 그 시점의
curHanState는 이미 첫 switch가 End2로 덮은 뒤였다** — DJongsung 판정이 항상
실패해 항상 "받침 없는 플러시" 분기로 갔다. 단일 받침(학+ㅗ)은 ELSE 분기가
정답이라 T10만으로 못 잡았고, 겹받침("랄가")에서만 드러났다.

**픽스**: 키 직전의 상태를 `prevState`로 저장(첫 switch 전)하고 End2의
겹받침 판정을 `prevState`로 한다. T13(랄가)/T14(Shift+r+k=까) 신설,
T1~T14 ×2 ALL PASS.

**레슨 16. 상태 머신에서 "지금 상태"를 검사하는 곳이 이미 상태를 덮은 뒤라면
이전 상태는 별도 변수로 저장해야 한다 — 첫 switch가 curHanState를 재기록하면
판정은 항상 한쪽으로 굳는다.** §10에서 단일 받침 시나리오만 테스트해 이 판정
오류를 통과시켰다 — 상태 분기별 케이스(단일/겹받침)를 모두 테스트했어야 했다.

## 13. 여섯 번째 보고 — "쌍자음은 처음부터 입력이 안됨" = 대문자 키코드 봉쇄

프로브 T14(Shift+r+ㅏ=까)는 통과했는데 라이브에서 쌍자음(ㄲㄸㅃㅆㅉ)이 아예
안 됐다. **원인은 두 층**:

1. `JKEdit::RespondMessage`의 한글 입력 분기가 `ev.keyCode`가 소문자
   `a~z`일 때만 오토마타로 보냈다. **라이브 SDL은 shift를 키코드에 이미
   반영해 'R'(0x52)로 오는데 대문자는 범위 밖이라 분기 자체를 통과 못 해
   조합이 시작도 안 됐다.** "처음부터 입력이 안된다"는 보고의 정체.
2. `ConvertKey`의 `modifier&0x0040 → key^=0x20` XOR는 "소문자 키코드+shift
   플래그"라는 옛 관례(DOS 하니스) 전용이다. 라이브 'R'+shift 플래그에
   XOR하면 오히려 'r'로 되돌아가 평자모 ㄱ이 된다.

**픽스**: ①분기에 대문자 `A~Z` 범위 추가 ②ConvertKey는 isalpha면 먼저
`tolower`로 소문자 통일 후 shift 플래그로만 대문자화 — 키코드 대소문자와
shift 플래그의 두 표현이 어긋나도 "shift 의도" 하나로 수렴한다. 프로브에
라이브 형태 T15('R'+shift+ㅏ=까)/T16('R' 무shift=ㄱ) 신설 — T1~T16(21체크)
×2 ALL PASS, ninja 전체(앱 DLL 전부) 재링크.

**레슨 17. 하니스 경로(소문자 키코드+shift 플래그)가 통과했다고 라이브가
통과인 아니다 — 라이브 SDL은 shift를 키코드에 반영한다. 상태/모디파이어의
"두 표현"이 어긋나는 지점은 정규화 함수 한 곳으로 흡수해야 한다.** T14는
하니스 표현만 검사했으므로 이 결함을 못 잡았다 — 프로브에 표현별 케이스
(라이브 형태/하니스 형태)를 나란히 넣는다.
