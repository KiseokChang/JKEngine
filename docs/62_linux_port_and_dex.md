# docs/62 — 리눅스 포팅 + DeX(안드로이드) 확장 설계 (2026-09-21)

사용자 요구: "리눅스에서 빌드하고 싶다" → 논의 확장 "나중에는 갤럭시 폰에서도 돌게".
브레인스톰(3절 승인)으로 확정된 요구:

- **DEX에서 미니멀 데스크탑 셸** — 태스크바+여러 앱 창
- 1순위 앱 = **전부** (터미널, 채팅+에이전트, vplayer, 셸+위젯 앱) — 사실상 엔진 전체 패리티
- LLM/에이전트 = **폰 단독 완결 + PC 백엔드 연계 둘 다 지원**
- 사용자 확정: 안 1(플랫폼 인터페이스 추출)·안 2(Termux)·안 3(네이티브 APK)은 배타 선택지가 아니라 **개발 1·2·3단계**

## 1. 근본 조사 (2026-09-21 실측)

우리 소스(src+apps+tools) 149파일 중 windows.h 계열 직접 include 22파일,
명명 파이프 36파일, BCrypt 29파일, D3D11/DXGI 10파일, ConPTY 5파일.
의존성이 플랫폼 레이어 한 곳에 몰리지 않고 설계 곳곳에 스며있는 것이 부담의 본체.

**핵심 발견 — 창 서버 모델이 이미 이식 친화적**: 데스크탑 전체(태스크바+앱 창)를
하나의 OS 창 안에서 SDL 표면에 직접 그린다. HWND 레이어링·TOPMOST·캡처는
OS 통합 기능(전체화면 OSD, 파일 대화상자, 캡처)에만 쓰임. 즉 "여러 창 셸"은
내부 창 관리자가 이미 처리 중 → 리눅스/안드로이드에서도 **OS 창 하나만 띄우면 셸 전체 이식**.

## 2. 설계 — "이식 불요 코어 + 플랫폼 어댑터"

```
[코어: 플랫폼 무관 — 3단계 공유, 이식 불요]
  터미널 로직(TerminalHangulInput §22 포함) · 한글 조합 · 앱(JKWindow 위 ImGui)
  프로토콜/승인 파이프라인(trust·permissions·파킹) · quickjs 워크숍 · LLM 엔진
  vplayer 디먹스/디코드(§7 분리 체계) · 리플로우 · 이벤트 카탈로그

[플랫폼 어댑터 — 단계별 새 구현]
  전송     명명 파이프(현행) → Unix socket(리눅스) → 로컬 소켓(안드로이드)
  pty      ConPTY → posix pty → Termux 부트스트랩/JNI 스폰
  암호     BCrypt → 수기 SHA-256 확장(jkbridge 선례)
  창/입력  SDL2 공통 + OS 통합(전체화면 레이어·캡처·파일 대화상자·IME)만 플랫폼별
  비디오   D3D11/NV12 표시 → SDL GLES 표시(소프트 디코딩 먼저) → VAAPI/MediaCodec
```

### 구성요소

| 구성요소 | 역할 | 비고 |
|---|---|---|
| `JKTransport` | 서버↔클라↔브로커 연결 추상 (프레임 인코딩·재접속) | 명명 파이프가 직접 드는 36곳이 이것만 본다. 승인 파킹·게이트 로직은 전송 위에 그대로 |
| `JKPlatformServices` | 암호(SHA-256)·pty·파일 대화상자·전체화면 레이어/캡처 | Win32 구현 현행 유지, 리눅스 구현 신설 |
| `VideoPresent` | 디코드 완료 프레임→표시 | D3D11/NV12 경로를 인터페이스 뒤로, 리눅스는 SDL GLES(소프트 디코딩) 먼저 |
| 리눅스 데스크탑 빌드 | jkwinserver 상당 (단일 OS 창+내부 창 관리자) | 셸 재설계 불요 — §1 핵심 발견 |
| Termux 패키지 | 리눅스 빌드+기동 스크립트+Termux:X11 연결 | 폰 실기기 1차 도달 경로 |

### 데이터 흐름 (변경 전후 동일 보장)

- 앱↔서버: 프레임 프로토콜·이벤트 카탈로그·승인 파이프라인 **전송 뒤에서 무수정**.
  바뀌는 건 "파이프에 쓰는 방식"이 "소켓에 쓰는 방식"이 되는 것뿐.
  jkbridge도 같은 계층을 물어 **PC 연계 모드가 자동 성립**.
- 터미널: pty 바이트 스트림 ↔ TerminalHangulInput §22 체계 무수정.
  한/영 단일 소유 규칙(§18)도 리눅스에서 그대로 유효 — OS IME를 안 거치므로 오히려 유리.
- 비디오: 디먹스/디코드 스레드 유지, 끝단 표시만 어댑터 교체.

## 3. 단계 로드맵

1. **플랫폼 경계 수술** — 어댑터 경계를 인터페이스로 뽑고 Win32 구현을 그 자리에 유지.
   완료 판정 = 기존 Win32 회귀 프로브 전부 GREEN (동작 변화 0 증명).
2. **리눅스 구현 + Termux** — 리눅스 데스크탑 빌드(터미널→채팅/에이전트→셸+위젯→vplayer 순)
   → 같은 빌드를 Termux 패키징해 폰 실기기 도달. 폰 LLM은 단독 모드+PC 백엔드 연계 모드 둘 다.
   **개발 환경 (사용자 확정 2026-09-21): 리눅스 머신을 띄워 VS Code Remote로 작업** —
   진짜 대상 환경이므로 WSL보다 우선. 1단계는 이 PC(윈도우+MinGW)에서 수행, 회귀 게이트도 Win32 프로브.
   단독 모드의 백엔드(원격 API 또는 폰 내 로컬)는 2단계 착수 시 확정 — 이 스펙은 모드 지원 자체만 요구.
3. **네이티브 APK** — 2단계 안정 후 별도 판단. DeX 네이티브 통합·배포가 필요할 때만.

## 4. 에러 처리

- **전송 끊김**: 재접속·세션 캡·타임아웃·`pending_result` 방침은 jkbridge에서 실증된
  체계(docs/57)를 `JKTransport` 계약으로 승격해 양 플랫폼 동일 적용.
- **서버 다중 기동 갈림** (docs/59 §16.1 파이프 이름 갈림 사건 재발 방지):
  뮤텍스 가드를 리눅스에서 `flock` 락 파일로 동일 봉쇄.
- **pty 사망**: 자식 종료→터미널 종료 흐름은 현행 ConPTY 규약 유지, 리눅스는 SIGCHLD 회수 추가.
- **폰 단독 LLM 백엔드 실패**: PC 백엔드 연계 모드로 안내(fallback 명시).
  PC 끊김 시 채팅/에이전트만 제한되는 것도 문서로 명문화.
- **IME**: OS IME 미개입(§18 단일 소유)이 리눅스/폰에서도 원칙 —
  fcitx/안드로이드 키보드 충돌을 설계상 배제.

## 5. 테스트

- **Win32 회귀**: 기존 .ps1 프로브+2연속 원칙 그대로 — 1단계 완료 판정(동작 변화 0 증명).
- **리눅스 회귀**: 헤드리스 C++ 콘솔 프로브 계열(terminal_hangul_probe 선례)로
  전송·pty·암호·셸 기동 스모크 신설.
- **폰 실기기**: 2연속 원칙 유지 실측 프로브+눈확인 (notes/files 창 선례).
- **하네스 분리**: .ps1은 Win32 전용으로 명문화 — 리눅스에서 흉내 내지 않음.

## 6. 리스크

1. 폰 vplayer 소프트 디코딩 성능 — 4K는 어려움 예상, 2단계 목표는 720p/1080p.
2. Termux 환경 제약(프로세스 스폰·권한) — 2단계 초반 실측 선행.
3. 안드로이드 프로세스 스폰 제약 — 네이티브 APK 갈 때만 문제(Termux는 무관).

## 7. 배경 결정 (why)

- **안 1을 추천한 이유**: 후속 플랫폼(Termux, 네이티브 APK)이 같은 인터페이스의
  새 구현으로 해결되고, 승인/보안 파이프라인 정합성이 유지된다. 안 2는 빠른 데모지만
  병렬 코드 경로가 남아 결국 안 1 작업을 미루는 것뿐. 안 3은 첫 가동까지 가장 김.
- **"Linux on DeX"는 삼성이 서비스 종료** — DeX 실현 경로는 Termux 얹기(2단계) 또는
  네이티브 APK(3단계) 사실상 2갈래.
- **스펙 위치**: 이 프로젝트 관례(docs/NN)를 따라 docs/62로. 스킬 기본 경로보다 관례 우선.

## 8. 착수 전 조사 결과 (2026-09-21, 3분도 조사 — 이 스펙의 비용 추정 정정)

§2의 "어댑터 신설" 추정 중 상당수가 이미 구현돼 있었다 (docs/43 분할 때 심어놓은 경계):

1. **전송 경계 이미 완성** — 모든 프레임이 `IWireTransport::{Write,Read}` 2시그니처만 통과
   (`include/ipc/JKWireProtocol.h:255`). Win32 파이프 API 직접 접촉은 `JKPipeTransport_win32.cpp`
   하나뿐이고 `JKPipeTransport_posix.cpp`는 62줄 스텁. **"36파일 IPC 수술"은 "posix 스텁 완성"으로 축소**.
   흠 2건: ①`CancelPendingIo()`가 인터페이스 밖 콘크리트 메서드로 새서
   `JKClientConnection.cpp:116`이 구체 클래스를 직접 부름 — 인터페이스 승격 필요
   ②`ReadMessage`가 길이 상한 검사 없이 `assign(header.length, 0)` — 페이로드 캡 필요.
2. **파일 대화상자 이미 플랫폼 무관** — JKFileDialog는 Win32 API 미사용 수기 브라우저,
   vplayer도 에이전트 채널 경유(ClientFileDialogApp).
3. **전체화면/캡처 이미 컴포지터 내부** — `engine/src`에 SetWindowPos/HWND_TOPMOST 0건.
   레이어 플래그(JKCompositorLayer)+이벤트만 존재. 플랫폼 어댑터 불요.
4. **ConPTY 단일 TU** — JKConPtyBridge가 이미 깨끗한 바이트 스트림 인터페이스
   (Start/DrainOutput/WriteInput/Resize/Stop)+비윈도우 스텁 보유. 파일 분할만 필요.
5. **vplayer에 엔진 소유 D3D11이 아예 없음** — 표시가 이미 SDL 일반
   (SDL_CreateTexture(NV12)+SDL_UpdateNVTexture+ImGui::Image, 픽셀은 shm 경유).
   **§2의 `VideoPresent` 어댑터 불요 — YAGNI로 소각**. D3D11 소유자는 SDL2 내부 백엔드뿐.
6. **암호 4개소는 수기 SHA-256 헬퍼 1개로 흡수** — BCrypt SHA-256×3
   (jkctl/jktriggers/JKDesktopShell, 포맷 "sha256:"+64hex 교차 일치 요구)+
   CSPRNG×1(jkbridge GenToken). jkbridge에 수기 SHA-1+셀프테스트 선례 존재.
7. **JKPlatform 헤더에 이미 OS별 분기 설계 존재** ("OS-specific .cpp" 명시),
   비윈도우 스텁 상당수 실구현(FileMtime100ns은 ::stat 실측).

→ 1단계(경계 수술)는 인터페이스 신설이 아니라 **기존 경계의 잔여 흠 수선(①②)+암호 통합+pty 파일 분할**.
2단계의 실질 작업은 posix 전송(Unix socket)·flock 가드·posix pty 구현이 본체.
