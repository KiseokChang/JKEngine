# 111 — JKDesktop 전략 원장: 세련된 GUI OS들의 철학에서 무엇을 배우고 무엇을 버릴까

작성 2026-11-15. 사용자 요청 원문: *"컴에서 돌리고, 폰에서는 DeX에서 돌리고 폰으로
제어는 목적. 이 목적을 염두에 두고 다른 세련된 GUI OS의 철학과 설계, 디자인을 공부해서
좀 진지하고 깊게 전략을 세우고, 문제들을 검토했으면"*

이 문서는 **결정 문서**다. 코드가 아니라 "무엇을 왜 그렇게 만들지"를 고정하고,
아래 4개 절로 나눈다: ① 목적 재정의 ② 참조 OS 해부 ③ JKDesktop 설계 원칙·디자인
시스템 ④ 문제 감사와 로드맵.

## 1. 목적 재정의 — "표면 3개, 두뇌 1개, 조종간 1개"

### 1.1 표면(surface) 매트릭스

| 표면 | 실물 | 입력 | 출력 | 역할 |
|---|---|---|---|---|
| **PC** | Windows 데스크톱 | 키보드·마우스 | 모니터 | **작업·저작** (문서, 코드, 대량 편집) |
| **DeX/TV** | 폰 → TV | 마우스·트랙패드·**폰 구두** | TV 1920×1080 (원거리) | **소비·감상·거실 제어** |
| **폰** | Galaxy Fold | 터치·음성 | 폰 화면 | **조종간(remote)** — 필요하면 자체 화면도 됨 |

핵심 문장: **"같은 OS, 세 개의 창. 두뇌는 하나, 조종간은 손안에."**

### 1.2 docs/105와의 충돌 — 명시적 정정 필요

docs/105는 "PC는 개발기일 뿐, 현장(거실)에 PC는 있을 수 없다 — 폰 단독 폐곡"을
**상위 전제**로 못박았다. 이번 요청은 그것을 **확장**한다: PC도 하나의 표면이다.

- 폐기하지 않는다: "거실 시나리오에서 PC 의존 금지"는 그대로 유효.
- 추가한다: "PC는 별도 표면으로서 1급 시민" — 단 거실 기능이 PC를 **요구**해서는 안 된다.
- 판정 규칙: **기능이 세 표면 중 하나라도 없으면 설계 결함**이지만,
  **거실 시나리오가 PC 없이 성립하지 않으면 더 큰 결함**이다.

### 1.3 "폰으로 제어"의 정확한 정의

지금 폰은 ① 컨트롤 앱(chg.jkcontrol) ② 오버레이 버튼 ③ 앱 내 MIC 로 제어 경로가
**3갈래로 흩어져** 있다. 전략적으로 하나로 정해야 한다.

> **정의**: 폰은 "입력 장치 + 상태 패널"이다. 명령은 단일 채널(`/talk` 계열)로
> 보내고, 폰 화면은 **현재 세션 상태(무엇이 떠 있고, 무엇이 재생 중인지)** 를 보여준다.
> 즉 폰 = 리모컨 + 인디케이터. 앱 실행기가 아니다.

## 2. 참조 OS 해부 — 무엇을 가져오고 무엇을 버릴까

각 OS에서 **구조적 교훈 한 줄**만 가져온다(표면적 모방은 하지 않는다).

| OS/셸 | 그들의 핵심 철학 | 가져올 것 | 버릴 것 |
|---|---|---|---|
| **Windows 셸** | 창 = 자유 배치, 태스크바 = 실행 상태의 단일 진실 | 태스크바의 **상태 표시 계약**(떠 있는 것 = 보이는 것), Alt-Tab 멘탈 모델 | 데모·유틸이 시작 메뉴에 섞이는 문화, 크롬(테두리)의 두터움 |
| **macOS** | 메뉴바 = **명령의 단일 표면**, 앱 = 문서 중심 | "명령은 한 곳에 모인다"(전역 명령 표면), 일관된 단축키 | 마우스 전제(원거리 TV에 부적합), 독의 화려함 |
| **ChromeOS** | 웹 우선, 창 최소, 상태는 클라우드 | **단순함의 강제**(창 관리 최소화), 기기 간 상태 동기 | 웹 종속, 로컬 자산 개념 부재 |
| **iPadOS** | 직접 조작, 파일 시스템 은폐 | **직접 조작 우선**(드래그·핀치), 계층 깊이 최소화 | 멀티태스킹의 혼란(Stage Manager), 파일 은폐 |
| **Android / One UI DeX** | 입력 모드 전환에 따른 **연속성** | DeX식 **입력 모드 적응**(터치↔마우스), 앱 상태 보존 | 알림·권한 피로, 설정의 깊이 |
| **GNOME** | 한 번에 한 작업, 크롬 최소, 개요(Overview) | **개요 = 창 목록의 정본**, 크롬 최소화, 제스처/키 일관 | 확장성 부재, 설정의 파편화 |
| **tvOS** | 10피트 UI, **포커스가 곧 입력** | **포커스 모델**(리모컨/구두에서 커서 대체), 큰 타입 스케일 | 폐쇄 생태계, 앱 간 이동의 빈약함 |
| **BeOS/Haiku** | 응답성 = 설계 목표, 작은 kit API | **"입력에 즉답"** 을 1급 지표로, 작은 계약(킷)으로 앱 작성 | 생태계 부재 |
| **webOS** | 카드 = 실행 단위, 제스처 중심 | **카드 메타포**(창 = 카드, 상태가 한눈에) | 제스처 과다 |
| **Tizen(현업)** | 기기 프로파일별 셸 | 프로파일별 셸 분리의 **명시성** | 레거시 크롬, 문서 파편화 |

### 2.1 교차 결론 5개

1. **포커스가 입력이다** (tvOS·GNOME): TV 앞에서는 마우스 좌표가 아니라 "지금 선택된
   대상"이 진실이다. 폰 제어에서는 **방향키/구두가 포커스를 옮긴다.**
2. **명령은 한 표면에** (macOS): 지금 우리는 우클릭 메뉴·태스크바·구두·폰 앱으로
   명령이 4갈래다. 전역 명령 팔레트(구두 + 텍스트) 하나로 모은다.
3. **상태는 한 곳** (ChromeOS·webOS): 창/앱 상태의 진실은 서버. 표면은 뷰다.
4. **크롬은 적게, 콘텐츠는 크게** (GNOME·iPadOS): TV 거리에서 크롬은 읽히지 않는다.
5. **즉답성이 기능이다** (BeOS): 우리는 이미 재드로잉/더티 추적에서 여러 번 당했다.
   "화면이 거짓말하지 않는다"를 테스트 가능한 계약으로 만든다.

## 3. JKDesktop 설계 원칙과 디자인 시스템

### 3.1 설계 원칙 (P1~P8, 위반은 버그로 취급)

- **P1 한 앱 = 한 목적.** 카탈로그에 `purpose` 한 줄이 없으면 데스크톱에 못 올라온다.
  데모·실험 앱은 `devOnly: true`로 격리(개발자 토글에서만 표시).
- **P2 조종간은 표면과 분리된다.** 폰 명령은 `POST /talk` 단일 채널. 오버레이·컨트롤 앱은
  **같은 채널의 다른 껍데기**일 뿐, 별도 로직을 갖지 않는다.
- **P3 포커스는 명시적이다.** 모든 창/셀은 `focused | selected | normal` 3상태.
  원거리(TV)에서는 포커스 링이 항상 보인다.
- **P4 거리 스케일.** TV는 **10피트 타입 계단**을 쓴다(본문 ≥ 화면높이/45, 라벨 ≥ /60).
- **P5 상태는 서버에만.** 표면은 파생 뷰. 표면별 캐시는 **세대(generation) 무효화**로만
  갱신되고, 캐시가 상태를 소유하지 않는다.
- **P6 화면은 거짓말하지 않는다.** "그렸다"와 "보인다"를 분리 계측(더티 rect 사건 +
  프레임 카운터). 재드로잉 누락은 로그로 잡힌다.
- **P7 점진적 능력.** 즉발 규칙 → 패턴 → LLM. 세 표면이 **같은 동사 집합**을 쓴다.
- **P8 크롬 최소.** 창 테두리·툴바는 콘텐츠 면적의 15%를 넘지 않는다.

### 3.2 타입·간격·색 계단 (초안 — 토큰으로 고정)

| 토큰 | PC | DeX/TV | 근거 |
|---|---|---|---|
| `text.body` | 14pt | **24pt** (화면높이/45) | 10피트 가독 |
| `text.label` | 12pt | **18pt** | 아이콘 라벨 |
| `text.title` | 16pt | **28pt** | 창 제목 |
| `space.unit` | 4pt | **8pt** | 배율만 다르고 비율 동일 |
| `radius.window` | 6pt | **10pt** | 거리에서 각이 부드러워야 |
| `hit.min` | 24pt | **48pt** | 원거리 클릭 오차 |

색은 이미 테마 토큰 3프리셋이 있으므로 **의미 토큰만 추가**: `surface.*`, `text.*`,
`accent`, `focusRing`, `danger`. 하드코딩 금지(현재 일부 리터럴 잔존).

### 3.3 창 크롬 규격(통일)

- 타이틀바: 높이 = `space.unit × 6`(TV 48px), 좌측 제목 + 우측 3버튼(최소화/최대화/닫기).
- 크롬에는 **텍스트만**, 아이콘 장식 금지(거리에서 안 읽힌다).
- 창 그림자 없음, 1px 테두리 + 포커스 링.

### 3.4 앱 카탈로그 큐레이션(목적 부여)

| 앱 | 목적(한 줄) | 노출 |
|---|---|---|
| 설정 | 기기·테마·권한의 단일 허브 | 기본 |
| 파일 | 자산·문서 접근 | 기본 |
| 노트 | 생각 기록(구두 입력 수용) | 기본 |
| 음악 | 로컬 음원 재생 | 기본 |
| 갤러리 | 사진 감상(TV 최적) | 기본 |
| **비디오** | 영상 감상(TV 최적) | 기본 — **현재 폰 미탑재** |
| 채팅 | 구두·텍스트 대화의 표면 | 기본 |
| 브라우저 | 웹(폰 브라우저 위임) | 기본 |
| 터미널 | 파워유저 셸 | 기본 |

## 4. 문제 감사 — 지금 무엇이 근본 문제인가

이번 세션에서 실제로 터진 결함을 **원인 계층**으로 재분류했다. 개별 버그가 아니라
**구조 결손**이 드러난 순서로 정렬한다.

| # | 증상(실측) | 근본 원인(구조) | 처방 |
|---|---|---|---|
| A1 | 메뉴/라벨 한글 깨짐 | 텍스트 경로에 **계약이 없음**(KSSM·아틀라스·비트맵 3경로 혼재) | 텍스트 파이프라인 단일화: 입력 UTF-8 → 글리프 소스 1개 → 캐시 키에 색·스케일 포함 |
| A2 | 테마 바꾸면 글자 사라짐 | **표면별 수동 더티 추적** — 재드로잉 사건을 사람이 빼먹으면 화면이 거짓 | P6 계측: 프레임 카운터·더티 rect 사건 로그 + 회귀 테스트 |
| A3 | 자산 업데이트가 폰에 안 풀림 | 캐시 무효화 기준이 **개수/최상위** 수준 | 자산 스탬프 = 패키지 갱신시각 + 하위 개수, 재추출 시 크기 비교 |
| A4 | 닫기 명령이 조용히 실패 | 권한 **기본값이 기기마다 다름**(파일 없으면 deny) | 첫 실행 시 `permissions.json` 기본 생성 + UI에 "막힘" 표시 |
| A5 | 런처가 "후진 앱" 서랍 | 제품/개발 경계 없음 → 데모가 사용자 앱과 동급 | P1 `purpose`/`devOnly` 메타데이터 도입 |
| A6 | vplayer 폰에 없음 | 플랫폼별 **능력 매트릭스 부재** — 조용히 빠짐 | `capabilities.json`(플랫폼×앱×기능) + 빌드 게이트가 누락을 실패로 |
| A7 | 제어 경로 3갈래 | 조종간 아키텍처 미정 | P2 단일 채널로 수렴, 껍데기만 여럿 |
| A8 | PC와 DeX가 같은 앱인데 상태가 다름 | **세션 개념 부재**(표면별 프로세스) | 세션 = 서버, 표면 = 뷰. 문서 열림·재생 위치를 세션 상태로 승격 |

## 5. 로드맵 — 3단계, 각 단계는 "측정 가능한 종료 조건"을 가진다

### 1단계: 정직한 표면 (2~3주)
- A1·A2·A3 처방 완료: 텍스트 파이프라인 단일화, 더티 계측 로그, 자산 스탬프.
- **종료 조건**: 테마 3프리셋 전환 × 30회 연속에서 "글자 소실" 0건(로그·스크린샷).
- P1 메타데이터 도입: 데모 앱 `devOnly` 격리, 데스크톱 셀 12±2개.

### 2단계: 조종간 통합 (3~4주)
- P2: 폰 오버레이/컨트롤 앱 → `/talk` 단일 채널로 수렴. 상태 패널(무엇이 떠 있나) 추가.
- P3·P4: 포커스 모델 + 10피트 타입 계단 적용.
- **종료 조건**: 폰만으로 "켜기·실행·닫기·재생·정지" 5동사 100% 성공(각 10회).

### 3단계: 세션 연속성 (4주+)
- P5·P8: 세션 상태 승격(문서·재생 위치·창 배치), PC↔DeX 이동 시 이어보기.
- A6: 능력 매트릭스 + vplayer 오디오(T8).
- **종료 조건**: PC에서 열던 문서를 TV에서 같은 위치로 열기(수동 조작 2회 이내).

## 6. 사용자 판정이 필요한 결정(이 문서의 열린 항목)

1. **PC를 표면으로 승격** — docs/105의 "PC는 현장 부재" 전제를 위 §1.2처럼 정정할지.
2. **폰 앱의 지위** — 폰을 "리모컨+상태판"으로 확정할지(자체 UI 축소), 아니면 폰 단독 사용도 1급으로 유지할지.
3. **vplayer 우선순위** — 무음 MVP 먼저 vs 오디오(T8)까지 기다리기.
4. **포커스 링 도입 범위** — TV(DeX)만 vs PC까지(마우스 사용자는 불필요할 수 있음).
