# docs/74 — 워크숍 단 2 트러스트 문 결정 메모

> 목적: docs/67 §7 질문 1(트러스트 모델 형태)의 판단 근거 제공 — 코드 변경
> 없음, 이 문서는 **결정 대기 중인 메모**다. 결정이 들어오면 설계 스펙으로
> 승격(docs/superpowers/specs/). 원료: docs/60 (프로토타입 자세=트러스트
> 배제), docs/67 단 2 (능력 선언형 후보), permissions.json 선례, docs/58 앱
> 도구 3단 게이트.

## 1. 문제

워크숍 슬롯의 작성물(스크립트 앱)은 **무승인 경계**에서 만들어졌다 —
프로토타입 자세(docs/60 헤더): 만든 사람이 곧 실행자라 트러스트를 배제해도
괜찮았다. 단 2(출하·나눔)는 이 경계를 깬다: 슬롯 앱이 **다른 환경/다른
사람(폰 등)** 에서 불린다. 이때 세 질문:

1. 남이 만든 스크립트가 내 환경에서 무엇을 할 수 있는지 **누가 판단하나**
2. 그 판단을 **어떻게 옮기나** (선언? 서명? 검수 기록?)
3. 어길 경우 **무엇이 막나** (fail-closed인가, 경고인가)

## 2. 후보 3형태

### A. 능력 선언형 (capability declaration) — docs/67 후보
- 매커니즘: MANI(또는 스크립트 헤더)가 쓰는 능력을 **선언** — 예:
  `capabilities=agent,fs,network,timer`. 엔진이 실제 호출 대비 선언을 게이트.
- 선례: **permissions.json 런타임 파일**(docs/57 레슨)·앱 도구 3단 게이트
  (docs/58)·trust_request 파이프라인(JKWindowServer :3986-4055, ask-capable
  집합 :7033-7052) — 전부 이미 존재. 선언형은 그 위 **한 층 추가**다.
- 장점: 저비고·즉시 도입 가능. 선언 자체가 문서화(수신자가 슬롯 스트립
  캡션에서 능력 목록을 본다). jkapp_script가 QuickJS 호스트 API를 통과시키는
  지점이 한 곳(JKScriptHost)이라 게이트 적용점이 좁다.
- 단점: **자기 선언이라 속일 수 있다** (선언 안 하고 호출). fail-closed 정책이
  없으면 선언은 장식. 선언 누락 앱이 많아지면 게이트 경보 피로.

### B. 서명형 (signing)
- 매커니즘: 작성자 전용 키 서명 → 수신자 검증(서명 무=거부 또는 경고).
- 장점: 진위·원작 보장 — "이건 내가 만들고 내가 보증한 버전이다".
- 단점: 키 운영 비용(생성/배포/폐기) — 현재 1인 워크스토키엔 과잉. 워크숍
  작성물은 **매 번 수정**되고 라이브 패치도 있어 재서명 마찰 큼(docs/67 라이브
  패치=QuickJS 정의 재평가, 서명 재계산 요건과 충돌).

### C. 검수형 (review)
- 매커니즘: 출하지 전 사람(=사용자 본인)이 검수하고 승인 목록에 등재.
- 장점: 사람이 책임 지는 유일 형태.
- 단점: 검수자=사용자 → 결국 A의 게이트를 사람이 수동으로 도는 것과 같다.
  규모 확장(타인이 만든 슬롯)에서만 의미가 생긴다.

## 3. 추천: A (능력 선언형) + fail-closed, 서명은 나눔 확대 시 2단계

근거:
1. **기반 투자가 이미 있다** — permissions.json·3단 게이트·trust_request.
   선언형은 신규 시스템이 아니라 기존 런타임에 인한 확장. B는 키 운영
   인프라가 신규.
2. **현재 나눔 범위가 좁다** — 첫 수신자는 본인의 폰/2번째 워크스토키.
   진위 보장(B의 강점)보다 능력 가시성(게스트가 "이 앱이 뭐를 합니다")이
   우선 문제.
3. **점진성** — A→A+B는 추가 방향(선언 위에 서명 덧대기)이지만 B→A는 힘들다.
   첫 날에 A로 시작하는 것은 포팅/계약에 버전을 붙이는 것과 같은 원칙
   (docs/67 사훈 — "첫날부터 버전을 붙여라").

### 설계 스케치 (A 채택 시, 결정 전까지 비구속)
- 선언 위치: MANI `capabilities=` (컴마 목록: widget/timer/canvas/agent/fs/
  network …) — jkx-pack의 MANI 필드 보존 수리(docs/60 §6, 플랜 I 예정)와
  연계: 재팩에도 선언이 살아남아야 한다.
- 게이트 위치: JKScriptHost의 호스트 API 공용창 — 선언 없이 호출되면
  **차단+정직 에러**(fail-closed, "capability 'fs' not declared in MANI").
- 수신자 UI: 슬롯 캡션/스트립에 능력 배지 — 선언 없음=능력 없음으로 표시
  (능력 없는 앱이 극단적으로 많아지면 선언 문화가 자연 성립).
- 접미 확장(나눔 넓어질 때): 능력 선언+서명 결합(선언을 서명 본문에 넣어
  훼손 방지) — 선언형 데이터 구조를 그대로 살린다.

## 4. 결정 요청 항목 (사용자)

1. 모델: **A 추천** — 채택/변경(B·C 혼합 등)을 결정해 주세요.
2. fail-closed 정책: 미선언 API 호출 = 차단(추천) / 경고만 통과.
3. 첫 적용 범위: 워크숍 스크립트 앱만(추천) / 모든 스크립트 앱.
4. jkctl pack MANI 수리(플랜 I)는 A와 독립 — 결정을 기다리지 않고 진행.

## 5. 결정 후 경로

결정 → 설계 스펙(docs/superpowers/specs/) → 플랜 → 구현(능력 토큰 표 +
게이트 + 캡션 배지 + 셀프테스트) → jkctl MANI 수리와 합쳐 단 2 출하 라인
개통(jkctl pack 뿌리 수리 → 슬롯→.jkx 출하 도구 → 갤러리).
