# /reports — 폰 리포트 수확·처리

폰 jkbridge 웹 UI에서 `/report`로 제출된 대화 기록(시각 포함)을 처리한다.
사용자가 폰에서 뭔가를 겪고 한 줄로 보낸 것이 곧 **결함 보고 후보**다
(참고: `usage_report_as_bug_report` 메모리 — 붙여넣은 사용 대화 = 즉시 진단 개시 선호).

## 1. 수확

`engine/build/state/bridge_report_*.txt` 를 mtime 내림차순으로 나열한다.

- 파일이 없으면 → **"처리할 리포트가 없습니다"** 를 친절한 한국어로 알리고 즉시 종료.
  (탐색 경로: 이 스킬을 실행하는 cwd가 어디든 절대 경로 `I:\progwork\JKENGINE\engine\build\state\` 기준)

## 2. 요약·분류

각 파일을 **원문 그대로** 읽는다(편집하지 않는다). 파일명에 리포트 시각
(YYYYMMDD_HHMMSS)이 있고, 내용은 `[HH:MM] 텍스트` 줄들이 누적된 폰 대화 원문이다.

사용자에게 각 리포트를 친절한 한국어로 요약한다: 리포트 시각, 대화 요지,
내가 본 결함 후보/질문/피드백 분류. **리포트가 2개 이상이면 처리 순서를
사용자에게 확인**한다.

분류 예:
- 결함 후보 — "안 열려요", "눌러도 반응 없음", 이상 동작 목격담
- 질문 — 기능 사용법, 의도 확인
- 일반 피드백 — 불편/제안

## 3. 결함 처리 — systematic-debugging 즉시 개시

결함 후보면 `superpowers:systematic-debugging` 스킬을 호출해 진단을 시작한다.
근인 분리 전에 절대 픽스부터 만지지 않는다.

**진단 도구 (이 프로젝트 관례)**:

- 라이브 재현: `agentctl` 원샷 (서버 재기동 후 MCP 연결은 죽을 수 있음 —
  agentctl이 정답 경로). 앱 도구는 `app_tool {app,tool,args}` 릴레이.
- 프로브: `engine/tools/probes/probe_*.ps1`, `> log 2>&1` 파일 리다이렉트
  (파이프 grep은 버퍼링 오판), **2연속 원칙** (1회 PASS는 반칙 — 플레이크 폭로 장치).
- 근인 3분리: 사용자 파일 손상 vs 제품 결함 vs 에이전트 표면 문제.
  외부 검증 도구 대조로 가설을 빠르게 기각/확정.
- 서버는 단일 인스턴스: `jkwinserver`가 파이프를 소유한다. `jkdesktop.exe`
  단독 기동은 클라 모드라 파이프가 없다. 2중 기동 금지.

**안전 규칙**:

- 유저 런타임 파일(`permissions.json` 등)을 **소유·삭제·복구 없이는 덮지
  않는다** — 과거 프로브가 전면 allow 파일을 소실시킨 사건 있음. 다루려면
  백업 + 콘솔 고지 필수.
- 위험하거나 외부로 나가는 변경은 진행 전 사용자 승인.
- 빌드: `engine/build`에서 ninja/cmake — temp는 `build_with_temp.sh`
  (I: 드라이브, exFAT 제약 스테일 판명 문서화됨).

**완료 기준**: 픽스 + 프로브(2연속 ALL PASS) + 라이브 재검증 + docs 기록
(docs-as-deliverables — docs/57/59 계열 §로 추가). 끝나면 다음 세션 재발 방지
레슨이 있으면 오토메모리에 기록.

## 4. 완료 표시

처리 끝난 리포트 파일은 `engine/build/state/bridge_reports_done/` 으로
**이동**만 한다(디렉터리 없으면 생성). 내용 편집 금지. 질문/피드백이던
리포트도 답변 후 이동한다. 이동이 실패하면 사용자에게 고지하고 원위치 유지
(다음 /reports에서 다시 제안됨 — 중복 처리되지 않도록 사용자와 확인).

## 5. 보고

마지막에 친절한 한국어로 정리: 무엇을 고쳤는지(커밋/문서 참조), 프로브 결과,
사용자 눈확인이 필요한 것. 폰 쪽 확인이 필요하면 폰에서 시험할 방법까지 안내.
